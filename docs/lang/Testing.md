# Testing

Testing is part of the proposed developer workflow. The first runner can be implemented independently of new language syntax: a test is an exported zero-argument function returning `void`, in a module under `tests/`, whose name starts with `test_`. The runner discovers exported tests from explicitly listed test modules; automatic file discovery is deferred. Tests must not depend on execution order. See [the illustrative tests](../../examples/testing/math-tests.nra), which import [Core](../../examples/guide/core.nra). A future runner must be configured to resolve that source root and the separately located test module; its configuration syntax is not yet specified.

The proposed `Test` built-in module provides `assert(bool)` and `assert_equal_int32(int32 expected, int32 actual)`. An assertion failure ends the current test, records its location and expected/actual values when available, and allows the runner to continue with other tests. A normal return passes. An unhandled runtime failure fails the test. The runner reports each test and totals, exits zero only if all selected tests pass, and exits nonzero for failures or discovery/build errors. Output format and exit codes beyond that distinction remain open.

The initial runner executes tests serially in a fresh process per test to isolate mutable global state and crashes. Test timeouts, fixtures, mocking, parameterized and property tests, coverage, and parallel execution are future work. Tests that need external resources should make setup and cleanup explicit. The example includes a commented failing assertion; uncomment it to exercise failure reporting once a runner exists.
