# Neura Virtual Machine

The Neura Virtual Machine (NVM) loads and executes a Neura Virtual Runtime image (`.nvr`). An image contains compiled neuron graphs, typed execution metadata, constants, and the host imports needed by the program. This specification defines the NVM execution contract. [NVR format](NVR.md) defines its binary encoding. [Neuron conversion and execution](../Backend.md) describes the implementation: its run limits, trap reporting, and embedding API, and the decisions the compiler takes where the language is open.

## Toolchain and distribution

```text
hello.nra -> hello.nir -> hello.nvr -> NVM
              typed IR     executable
```

The compiler can materialize versioned NeuraIR as a `.nir` file before optimization. A build from source can pass the same representation internally. Both routes validate NeuraIR, apply the selected IR optimization pipeline, convert the result to neuron graphs and execution metadata, and encode the NVR image. A `.nir` reader must preserve types, symbol identity, region structure, evaluation order, and effects. The human-readable IR listing is a separate interface.

The compiler distribution provides these commands:

```sh
neura emit-ir hello.nra -o hello.nir
neura build hello.nir -o hello.nvr
neura build hello.nra -o hello.nvr
neura run hello.nvr -- arg1 arg2
```

`neura run` loads the image, binds the selected host services, and passes arguments after `--` to the entry function. The loader and executor form a reusable NVM library. A runtime-only distribution uses the same loader and execution contract. A compiled image can move between supported hosts with compatible format and service versions. A [native executable](../lang/Standalone.md) is a runtime-only distribution with a CPU launcher. Its container carries the unchanged NVR bytes and the runner policy: the capabilities, the run limits, and the task settings (the task, queued-message, and pending-request limits, the quantum, and the parallel worker count). The same loader and execution contract apply after extraction. `NEURA_RUN_OPTIONS` can lower the limits and the worker count and cannot change the quantum, which decides how tasks interleave.

## Graphs and continuations

A function has a signature, a frame layout, and an entry block. Each block evaluates a feedforward neuron graph, then takes one declared exit. Blocks can share graph definitions. A loop repeats blocks through continuations. A call uses the callee's entry block and its own frame. The graph produces an exit selector and payload bits. NVM interprets the selected exit descriptor and transports its typed values.

The reference graph profile uses signed 64-bit integer weights and biases, with identity and ReLU activations. For a node, NVM starts with its bias and visits incoming edges in ascending source index order. Each multiplication and running sum uses checked signed 64-bit arithmetic. Overflow traps before the activation. Identity returns the sum. ReLU returns zero for a negative sum and the sum otherwise. Node evaluation order follows the stored topological order. A backend must produce circuits whose intermediate arithmetic is valid for the input domain it claims to support.

An implementation may compute graph output lanes by another method when they equal the reference values and reference evaluation does not overflow. If the method cannot establish both conditions, the reference evaluator supplies the result or reports the overflow.

At the graph boundary, each value occupies a sequence of bit lanes. Lane zero is the least significant bit. Booleans occupy one lane, and integers occupy their declared width with two's-complement encoding for signed values. References cross the graph boundary as 64-bit opaque handles. Every output lane consumed by the selected exit, including the selector, must be exactly zero or one. A selector outside the block's exit table traps. Source arithmetic and comparisons are expressed by the graph, including checks and exits for specified arithmetic failures. Checked neuron arithmetic is an execution rule for the target and is distinct from the source language's arithmetic rules.

A typed value descriptor can read a frame slot, a constant, or an output lane slice. The runtime transports opaque handles and checks their type and validity when used. Language-level equality, arithmetic, and control decisions are represented in the circuit. Execution metadata can transport a constant or a live reference without routing it through a neuron.

### Graph devices

A graph device belongs to one validated image. Each job sends a graph index and its binary input lanes. The device either returns the exact output lanes in the graph's output order or declines the job. A device failure also declines the job. The executor evaluates declined jobs by reference, including the reference evaluator's first-overflow diagnostic. The executor checks selectors and consumed output lanes and owns every continuation, slot, heap object, resource limit, and host interaction. Device evaluation has no host import or trace entry.

For the same image, arguments, limits, and host completions, an execution must agree in every mode, with any device, and whether it runs alone or as a member of a fleet, on:

- every exit selection, slot assignment, state operation, and host request, in order, with the same arguments;
- the terminal outcome: status, or the trap's kind, reason, detail text, function, block, and caller list;
- `steps`, `peak_heap_cells`, `function_steps`, and the host request count;
- standard output and the trap diagnostic on standard error;
- a trace written by `--record`, byte for byte, and the result of `--replay`.

The following can differ:

- Wall time and process start-up time.
- Which evaluator computed a given graph, and therefore the `gpu:` line that `--stats` adds.
- Runner errors that exist only for the GPU options.
- Peak memory of the process: a fleet holds several members' heaps at once.

A device can expose its graph shapes in image order and a failure reason to a placement wrapper. The wrapper can then omit graphs excluded by the device's table limit or demoted after an escape. An empty shape view leaves the wrapper with the image's static shapes. A failure reason retires the device from automatic placement for the remainder of the run.

Embedders can split a block transition using `Execution::begin_step`, then `finish_step` with exact output lanes or `fail_step` with the reference overflow's node index. Begin charges the block's step and resolves its inputs before evaluation. The input view remains valid until the step is settled. Beginning another step or calling `advance` before settling it is an API error. Finishing with the wrong number of lanes rejects the call and leaves the step open. With no device in `RunLimits`, `advance` evaluates by reference.

### Execution tiers

A tier is a method of computing a block's graph outputs. Every tier is held to the equivalence rule above: it may supply a block's output lanes only when they equal the reference values and reference evaluation of the graph does not overflow. The invariants listed under [Graph devices](#graph-devices) hold whichever tier evaluates a block.

**Tier 0, reference.** The evaluator of [Graphs and continuations](#graphs-and-continuations): every node in stored order with checked arithmetic. It is the oracle for every other tier, and it supplies the result, or reports the first overflow, whenever another tier does not.

**Tier 1, lifted blocks.** The library in `src/lift` (`neura_lift`) turns a block into a short program of native 64-bit operations over its whole input values. It accepts a block only when it establishes both conditions of the equivalence rule for every input of the block:

- **Structural proof.** A lifted form states the block's values, its exit condition, and its checks as typed operations ([Numbers](../lang/Numbers.md)) over the block's inputs. Regenerating the block from the form with the compiler's circuit library (`neura_circuit`) must yield a block and a graph identical to the image's. The equality is exact, so the graph computes exactly what the circuit library builds for those operations. Nothing weaker is accepted: no sampling, no exhaustive evaluation, and no source of the form, including a hint stored with the image, is trusted. The form comes from the image's `LIFT` section ([NVR](NVR.md#lift-hints)), where the converter records the operations it built each block from, or from the decompiler's structural search ([Decompiler](../Decompiler.md#lifting)), which samples the graph by reference only to choose candidates. A converter-recorded form is *shared*: a node it uses twice is one computation, as the converter computed it once, and it lists every operation in the order the block performs it, including one whose only effect is a check, so regeneration builds the block's neurons and checks in the same order.
- **Overflow proof.** Interval analysis gives every wire a range that holds for every 0/1 input. Starting from the bias, each product and each partial sum, in the reference order, must stay within signed 64-bit arithmetic. Each graph output lane must also be exactly 0 or 1. Intervals lose the correlation between the terms of a sum, such as a sum lane and its carry, so two exact refinements narrow a wire's range before its readers use it. Wires whose weighted sum is known to stay in a small range form a group: a threshold pair `relu(L + b) - relu(L + b - 1)` is 0 or 1 for any integer `L`, and so are two halves of a selection once case analysis shows it. A bounded case analysis also evaluates a wire for every assignment of a small cut of wires below it, with each group as one variable. Where the cut's assignments are too many to enumerate together, because a carry chain or a run of selections links every wire of the cut, an exact elimination computes the same range by dynamic programming along the cut's cone in stored order: a state holds the values of the wires a later node still reads and the range of the part of the sum already known, a wire is summed out after its last reader, and states that then agree merge, keeping both ranges. Its cost grows with the number of wires held at once, not with the cut: a ripple carry holds one carry. It narrows the sums and selections of the float circuits node by node, after which their output lanes follow. An output lane whose range is not within [0, 1] is accepted only for one more reason: it sums equality tests that pairwise require opposite values of some lane, so at most one of them holds. Every argument covers all inputs; none samples.

The overflow analysis first runs without its two refinements. Its intervals are then wider but still sound, so a proof it finds is as valid as a refined one, and for most graphs it is found in a fraction of a millisecond. Only a graph it cannot settle gets the refined analysis, whose case analysis can be bounded by a count of work. Running out of work decides nothing: the analysis stops, and it may be run again with more. A bound changes only whether a proof is found, never which. Both proofs of a graph hold for every block that uses it, so a runtime proves each graph once.

The refined analysis is told where to look first. While the structural proof regenerates a block, the circuit library records which gadget instance built each neuron and which wires that instance was given. For each neuron the analysis first tries the cut through those wires, which is the cut the gadget's own argument uses: a multiplier column is bounded through its carry and its partial products rather than through the input lanes far below them. This record is advice and not evidence. A range is established only by evaluating a neuron over every assignment of a cut, which is sound for whatever cut is tried, so wrong advice can cost time or a proof but cannot make one. The analysis runs up to three times: with the advised ranges left to stand, then with its search after each advised cut, then without advice, and only the last run rejects a graph. The case analysis keeps each enumeration under a description of the whole computation with its wires renamed, so the identical cells of a multiplier or the steps of a long division are evaluated once.

The lowering then gives each operation an exact native form. Integer operations use the stated width and signedness, with the failure conditions of the circuit's checks. When an operation fails, the block takes the trap exit of the first failing check, as the selector would, or declines the step when the block has no trap exit for that check. Float operations are lowered only where hardware arithmetic matches the circuits bit for bit. Each binary32 and binary64 operation runs on the hardware, and every NaN result is replaced by the canonical quiet NaN. Comparisons, negation, truncation to integers, and widening conversions of any format are exact. Narrowing to binary32 is rounded by the hardware. Three operations are not lowered: binary16 and bfloat16 arithmetic, and conversions to a 16-bit format, whose rounding the hardware does not provide. A block that contains any of them stays on tier 0. Every other float operation of binary32 and binary64, addition, subtraction, multiplication, and division included, passes both proofs; the proof of a binary64 multiplication or division costs a few tens of milliseconds, the most of any operation, so a block that contains one is lifted only after it has run long enough to repay it (below). A float block runs on tier 1 only with the default floating-point environment, which rounds to nearest even and neither flushes subnormals to zero nor treats them as zero. WebAssembly (`nvm.wasm`) lowers them too: its `f32` and `f64` instructions round to nearest even, keep subnormals, and have no other environment, and the canonical NaN replaces the NaN bits the standard leaves open. On other platforms, or where `FLT_EVAL_METHOD` is not 0, no float operation is lowered. When a lowered block meets another environment, it declines the step.

Forms come from two sources. The converter records one for every block it can describe (multi-statement blocks included) in the optional `LIFT` section, and keeps only those whose structural proof holds against the block it emitted. Without a hint, the decompiler's search, extended with integer bitwise operations and shifts, which it tries only after the decompiler's own vocabulary fails, recovers one or two operations over at most three input values. A lowered block depends on the graph, the block's input types, its selector, and each exit's kind, trap reason, and output lanes. It does not depend on slot numbers, constants, targets, or the function, so blocks that share a graph and those share one result. A block whose form is not found, or for which either proof or the lowering fails, stays on tier 0. A block whose graph has no neuron needs no proof: nothing can overflow, and each output lane is an input lane, which holds a bit. Tier 1 reads such a block's lanes straight from its input values.

#### Tier 1 in the executor

`neura run`, `neura test`, `run --each`, fleets without a graph device (or after they drop one), the parallel items of a run, and task images all use tiers 1 and 2 by default. A step of a block on tier 1 is a reference step with another way of computing the graph's outputs:

1. The step is charged and the scheduling decision made exactly as by reference, and the block's slot inputs are checked for initialization in input order. An uninitialized slot traps with the same detail, at the same step.
2. The input values are read whole from their slots and constants, without expanding them into lanes, and the lowered block computes the selected exit and every value an exit reads. When a check fails, it selects the trap exit of the first failing check, as the selector would.
3. The exit is committed by the reference commit: values are resolved against the pre-transition frame in the same order, references read from lanes are checked against their types as before, and the assignments, state operation, call, return, or host request follow unchanged.

When the lowered block declines a step (a float environment other than the default, or a failed check whose trap exit the block lacks), that step is evaluated by reference. So is every step of a block without a lowered form. Nothing else changes: one block is one step, `steps`, `function_steps`, `peak_heap_cells`, every trap's kind, reason, detail text, location, and caller list, the host requests, standard output, and a `--record` trace are those of tier 0, and so is a `--replay`.

The lifted blocks of an image live in one `nvm::TierCache` that every run of the image can share (`RunLimits::tier_cache`): `neura run` and `neura test` create one per image, a fleet without one shares its own among its members, a run without one keeps its own, and parallel items use their run's. A lowered block, once published, is immutable. A block with a hint is proven after it has run 4 times, so a block that runs only once or a few times, as start-up code does, is never proven; a block without one is searched for after 2,000 runs, both counted over every run that shares the cache. The refined overflow analysis may use at least about 16 ms of work, enough for a binary64 multiplication or division at the first attempt, and beyond that work in proportion to the steps the block has run times its graph's edges, about twice what the block has cost on tier 0; a search may use wall time in the same proportion, an eighth of that cost. These figures were chosen by measuring the CPU time of the wall-clock benchmarks ([Benchmarks](../Benchmarks.md)) and of `neura test` over standard-library areas, where they lift float blocks soon enough that proving, not tier 0, is most of a short float program's time, without slowing start-up. An attempt that runs out keeps what it settled, and the next attempt resumes there rather than starting over; it is made once the block's allowance has grown enough for the rest, judged by the share of the graph the attempt reached (at least eight times as many runs). The searches of one image stop after 250 ms in all. A proof or search that fails is remembered and never repeated. A block whose graph is too large to model is not searched: the search keeps, for every neuron, the input lanes it depends on, and gives up past 4,194,304 such entries in all (about 200 MB; a block that adds 300 parameters passes it, and without the limit took 12 GB and 40 s). Such a block stays on tier 0, and `--tier-stats` gives `graph too large to search` as the reason. The decompiler's recognition (`lift::recognize`) shares the limit, so it too leaves such a block unrecognized. All of this decides only which blocks run lifted, and when.

#### Tier 2, regions

Tier 2 runs proven blocks one after another without returning to the step dispatcher between them. Its unit is a **region**: blocks of one function, entered at one block, compiled together into one program (`src/nvm/tier2.hpp`).

**Formation.** A region starts at a block that tier 1 runs lifted, wired, or empty, and takes in the blocks reachable from it through continue exits and through the state operations that run inside a region (below), as long as tier 1 runs each of those lifted, wired, or empty too, up to 128 blocks. Each block keeps its exits: one that leaves the region is taken by tier 1. The dispatcher counts its arrivals at a block, over every run that shares the cache, and forms the block's region at the thousandth (at the first under `NEURA_TIER_EAGER=1`). While blocks the region would reach are still being proven, formation waits, up to eight times as long, and a region formed without them is formed again later, at most four times. No region starts at a block with no exit that can stay in one. A formed region is immutable and shared by every run of the image, like a lowered block.

**What a region runs.** Inside a region a block's exit is one of:

- a continue exit to a block of the region, followed directly, with its poll when it has one;
- a continue exit to a block outside the region, after which the region **leaves**;
- a state operation that only reads or writes storage that already exists: `ReadTag`, `ReadField`, `WriteField`, `ReadGlobal`, `WriteGlobal`, `ReadLength`, `ReadElement`, `WriteElement`, `ReadVersion`, `TextEqual`, `ClassIs`, `ClassCast`, and `ScalarText` when it selects one of an enum's names. The region calls the executor's own state-operation code with the same arguments, so its checks, traps, and trap texts are the same;
- any other exit (a call, return, host request, scheduler operation, trap, message trap, or a state operation that allocates, grows, frees, builds text, or calls a kernel). The region does not take it: it **deoptimizes** at the block, and tier 1 runs the block.

**Steps and polls.** Each block a region completes is one step. Steps are added in bulk when the region ends: to the run's count, under `--profile` to the region's function (a region never leaves its function, so the attribution is exact) and to the running task. Nothing inside a region reads the count. The region's entry, and every block a loop in it returns to, is a checkpoint: there the region checks that the most blocks any path can take before the next checkpoint or the region's end fits in what remains of `--max-steps`; that under a scheduler the most polls such a path takes keep the task's count below its quantum; and, in a fleet, that the blocks fit in the rounds the fleet allows. If one does not fit, the region deoptimizes at that block and tier 1 runs on, one block at a time, so the step-limit trap, the end of a turn, and every fleet round happen at the block and with the counts of tier 0. A fleet counts a region's blocks as rounds.

**Deoptimization.** A block commits its exit (its assignments, a state operation's result, its poll, and its step) only after everything that can fail in it: a check of a lifted operation, a reference read from lanes, a state operation, a selector. When one fails, or the exit is one the region does not take, the region writes back every slot it caches, with the frame as it was when the block was entered, and sets the frame's block to it. Tier 1, and tier 0 when tier 1 declines, then runs that block from that state, producing the trap's kind, reason, detail text, function, block, and caller list, or the call, return, request, or allocation, with the reference code. A return of several words (NVR 1.7) and a call to a function that has them run in function programs and in tier 3 ([NVR](NVR.md#multi-word-results-17)). A program's return keeps one register per word and writes every word to the caller's consecutive result slots, flags set, as the reference does; the analyses that prove a slot's width or initialization count every word a call writes. In tier 3 a call's first word is the call's value and each later word is a `ResultWord` that reads what the callee's return left in the context (a return passes them through the context, and every return of such a function goes through the return helper, which also writes the caller's frame). An inlined call has a phi per word, and a deoptimization inside the callee rebuilds the frame, whose later return writes every word in tier 1. A function that returns more than 64 words stays on the program interpreter. The component operations (NVR 1.7 `read-component`, `write-component`) and the state operations on an array or list of aggregates run in programs too ([NVR](NVR.md#aggregate-elements-17)): a component read or write and `read-length` and `read-version` run inline in a region or program through the reference state operation, which divides the word count by the components per element; in tier 3 the component accesses are heap accesses with the bounds check against the length in elements, whose loads and stores are their own alias classes by component, and `read-length` divides the count word. Allocation, repeat, append and removal on such a collection are helpers (program) that run the reference operation, so the heap accounting is the reference's. The region operations (NVR 1.7 operations 27 through 32, [Storage regions](#storage-regions)) are helpers of a function program, which run the reference operation on the task's region stack, so the release order, the stack-cell accounting and every trap are the reference's; a region (tier 2's unit) still ends at one, which tier 1 runs. The return of a function that enters a region is a program op: it releases the regions the frame left open before it pops the frame, as the reference return does. Tier 1 commits every one of these the same way, so a run's result, steps, and peak heap cells do not depend on the tier.

**Slots and the collector.** A region caches the slots it reads and writes in registers and writes them back, with their initialized flags, whenever it leaves or deoptimizes. Nothing in a region allocates, so no collection can run while a reference lives only in a register, and at every safepoint the frame holds what it holds at tier 0. A slot that some path reads before writing must be initialized when the region is entered, or the region is not entered; every other read follows a write on every path, and a slot never becomes uninitialized in its frame, so no read inside a region can find one uninitialized.

**The region program** caches slots in registers, loads constants at entry, runs each lifted block's operations with the code of tier 1, branches directly between blocks, and has explicit write-backs, deoptimization points (each naming the block it re-runs; the slot registers are the map), checkpoints, and loop heads, so a native compiler can take it as its input. A few local rewrites, each justified inside the region, make it shorter: a mask is dropped where an analysis of the bits each register can hold shows it changes nothing (slot registers are checked against their types' widths at entry, or the region is not entered); a checked addition or subtraction of 1 becomes unchecked when a comparison on every path to it shows the counter is below its type's largest value (or above its smallest), the check staying in the image; operations whose results nothing reads are removed; and a result is written into its slot register directly when nothing between the operation and the commit can deoptimize or reads the slot. A region runs as native code where that is enabled (below), and otherwise in a portable interpreter.

#### Tier 2, function programs

A **function program** is the other unit of tier 2: one program for every block of a function, which takes the place of the function's regions. Programs form by default where tier 3 runs natively (below), and under `NEURA_TIER3=interp` or `NEURA_TIER_PROGRAMS=1`; where none of these applies (`NEURA_TIER3=off`, or a run without native code, no tier 3 code generator or `--jit=off`), no program is formed, regions are used, and nothing below applies. Under `NEURA_TIER_PROGRAMS=1` alone a program runs in the portable interpreter.

Tier 3 turns a function program into SSA form with a lazily written frame (a native program): an intermediate representation, a verifier, an interpreter of that representation, and, on x86-64 Linux, machine code generated from it. It is the default where native code is available (x86-64 Linux, with `--jit` not `off` and `NEURA_JIT` not `off`): with `NEURA_TIER3` unset a run is a `NEURA_TIER3=native` run, and everywhere else it runs as it did before tier 3 (function programs are not formed, `--tier-stats` has no `native` lines). `NEURA_TIER3=off` is that earlier behavior everywhere, byte for byte. `NEURA_TIER3=native` (machine code) and `NEURA_TIER3=interp` (the IR interpreter) ask for tier 3 explicitly and are testing aids; `native` where native code is not available runs on the IR interpreter and says why in `--tier-stats`. Machine code is generated for a program's entry 0 when it is built and for every other entry on its first use; each entry has code of its own, made from the blocks it reaches, and an entry whose code cannot be generated runs on the IR interpreter. A program is built once its checkpoints have been reached 1000 times (once under `NEURA_TIER_EAGER=1`) and the functions it calls have settled programs of their own, so that the inliner and the class tests of its dispatch sites find them: while a callee it calls has no settled program, the build waits and is considered again every eighth of the threshold in arrivals, goes ahead once none of the unsettled callees has run (a block arrival counted) over two such checks in a row, and at the latest at 16 times the threshold; a callee that does not run delays the build by a quarter of the threshold. A run enters the program where it would enter the function's program; what a run does is the same either way.

Serial native execution with `--tier-stats` uses the same frame recovery policy as ordinary execution. The timer reads the clock when the execution category changes. The debugger, verifier and shadow replay retain their frame inspection behavior.

**On-stack replacement (OSR).** When the interpreter transfers into a native program at a nonzero loop entry, Tier 3 can specialize the graph to the single entry the interpreter used. The entry stub loads the original frame and leads into the reachable loop. The optimizer can then use the same preheaders, invariant motion, and frame liveness proof as it uses at function entry. Tier 3 publishes the specialization when it hoists a heap preflight. The original graph serves other entries and remains available when specialization cannot generate code or a checked rebuild has no heap preflight. Tier 3 retains an OSR template for loop entries that can reach an indexed access in the original graph. On first use it tries at most two such specializations per native program version. After the last possible attempt it releases the template. A back-off rebuild carries the original loop exclusions into its single-entry graphs. `--tier-stats` reports the number of OSR specializations generated and entered.

With deferred proofs disabled, one native cache and one execution can retain up to 110 Tier 3 program objects for a single function across program generations, variants and checked rebuilds. Additional executions can own their own checked programs. Each generic lazy entry can retain a machine-code mapping, and code size depends on the compiled function and its entries.

An instrumented x86-64 Linux build of runtime commit `7ab591a1164a94cedaad87bb7f8202ec983784ab` recorded mapping lengths and lifetimes at successful Tier 3 `Program::load` calls and at release. Across 26 cold qualification workloads, the largest observed total for a single function was 6,012,891 bytes of emitted code in 11 simultaneously live mappings. Those mappings occupied 6,033,408 bytes on 4,096-byte pages. These figures cover executable mappings only. Both maxima came from function 8 in `log-analytics.nvr`, built from the frozen `tests/bench-wall/fixtures/log-analytics.nra` fixture in commit `b897bcc7a06259ffa36a02011b2cf05aa1310b76`. The run used the following command with the instrumented runtime.

```sh
neura run --stats --gpu=off --tier=2 --jit=on --max-steps 1000000000000 \
  --max-heap-cells 4294967296 --runtime=off --parallel-workers 1 \
  log-analytics.nvr -- 425000
```

**Tier 3's passes.** After a program is built, passes rewrite its IR, in this order, and the verifier runs after each one under `NEURA_TIER3_VERIFY=1`: constant folding (a lifted op on constants through `lift::evaluate`, and a branch, switch or dispatch on a constant), the replacement of phis of one value, value numbering of pure ops and of checks a dominating one covers, range analysis (an interval for every integer value as an unsigned register and as a signed value of its width, widened after two growths, narrowed on each branch edge), check elimination, loop-invariant code motion, a second value numbering, removal of unused pure values, and the recomputation of every checkpoint's length on the graph that is left. A check is removed only when the intervals of its operands make `lift::evaluate` report no failure at the instruction's width and signedness: an overflow check becomes the wrapping form, and the checks of a division, a shift count, an index, a conversion, and a switch selector go the same way. The interval arithmetic is done in 128-bit integers, so no bound can overflow. A loop with one header that dominates its body gets a **preheader** that every entry into the loop passes through, the entries from the interpreter included; invariant pure values and checks that run on every path of an iteration, with no effect before them, move there, a check keeping the state of the loop head's entry, so that a failure resumes tier 1 at the head. Where a loop variable starts at a value the interpreter hands over, the facts the loop's eliminations need about it are **guards** in the preheader (`init >= 0` for an index, `init <= bound` for a loop that ends on `!=`); a guard that fails deoptimizes at the loop head and tier 1 runs the loop. Which passes did what is counted per program, and `NEURA_TIER_DUMP=1` prints the counts.

For loops that preserve heap metadata, a preflight may also hoist stable heap checks and bound element accesses against the actual collection length. An affine index needs a shared subscript bound and a guard that the original arithmetic widths can represent the resulting indices. A single-entry graph can prove this relationship when its entry and loop tests establish both subscript bounds. After three preflight failures at the same original loop header, the run rebuilds that function’s native program with the loop’s checks in place. Subsequent calls and loop entries in the same run use the checked version. A failed preflight always resumes at the original header before the loop’s effects and step charges. `--tier-stats` counts the back-offs.

**Tier 3's initialized flags at an entry.** A native program's code reads the initialized flag of a slot from the frame where a run enters it, and every slot a loop assigns has a phi of its flag at the loop head, so that code that knows nothing of the flags at its entry keeps one live phi per slot through the loop. Two facts remove them. At entry 0 of a function program, the flag of every slot but a parameter is 0: a call leaves the callee's frame so, and a run that the dispatcher enters at entry 0 in a frame where one of them is set is refused. At any other entry, the program carries what its image proves of the frames that arrive at that entry's block, however they got there (`Region::Entry::flags`, `analyse_flags` in `src/nvm/tier2.cpp`): over every exit of every block of the function, with the parameters initialized at block 0, a call's or state operation's result slot assigned on the exit's resume edge, and the flags that can reach a block collected as a set of vectors (at most 256 per block; a function that exceeds it has no facts), a flag that is 0, or 1, in every vector is known, and the flags of slots whose flags are equal in every vector are one value, as are the phis that join them. A slot that a host request or a scheduler operation writes has no fact. `NEURA_TIER3_VERIFY=1` checks the facts of an entry against the frame each time the dispatcher enters it, and aborts on a difference. Phis of one block whose inputs are congruent over the edges of the code being generated are one value. `NEURA_TIER3_ALLOC_TRACE=1` prints, for each unit of code generated, its blocks with the phis, the location of every live value at the block's start, the locations of each instruction's operands, the moves around it, and the moves on each edge.

**Tier 3's inlining.** Before the passes, a native program can inline a callee's function program into the caller's SSA. The call arguments become the callee's parameters. A frame-state level retains the information needed to materialize the callee's frame, including its slots, initialized flags, return slot, and resume block. A deoptimization rebuilds every inlined frame so Tier 1 resumes with the original frames, steps, and callers.

An inlined callee has a function program at block 0 that reads only parameters on entry. It must fit the caller's argument and result slots, stay within four levels of inlining, and avoid recursion on the inline chain. The general limits are 64 blocks and 400 program operations per callee after nested inlining, and at most eight times the original operation count and 20,000 operations for the native program. Storage-region operations require a real frame, so they prevent inlining. A callee generally needs to have no remaining helper, call, or frame write-back. When an admitted callee introduces the first inline kernel in a caller, the caller carries the kernel step count through its entries, block joins and recovery states. For a verified state exit whose short scalar append shares a selector and continuation with an `AppendRun` arm, the inliner keeps the short append inline and outlines the `AppendRun` arm. On that arm it deoptimizes before the selected block commits, so Tier 1 replays the original block and executes `AppendRun` with its original arguments and resume point.

At a dispatch or closure site that has multiple table entries, the interpreter records up to eight distinct tags. If they select at most six exits whose callees meet the inlining rules with at most eight blocks each, the inliner adds class tests in recorded order. Other tags reach the original dispatch. A one-entry table can use the direct-call allowance of 64 blocks without a profile and keeps the original dispatch check. The wider dispatch allowance and outlined helper path have an additional estimated growth limit of 6,000 per caller and 12,000 per native program. The estimate charges for cloned blocks, instructions and recovery frame states. Under `--profile`, the runtime leaves the calls in place so each function's steps are attributed as in Tier 0. The `tier: native programs` line reports inlined calls and dispatch sites with class tests.

**Tier 3's heap access.** A native program reads and writes the heap inline through the heap's published layout (`src/nvm/heap.hpp`): a field, element, length, tag, version or global read or write is the check its state operation makes (the handle names a live entry of the static type, the field or global is initialized, the index is below the length) followed by the access, and a failing check resumes tier 1 at the block, which traps there as the reference does. A field's offset is a constant only when every layout the static type admits has the same number of initialized words; otherwise it is computed from the entry's own field count. Elements are read and written at the storage width, which is the declared width until a wider value widens it; a value that may not fit is stored through the heap. Allocating an object and appending to a list are done inline when the heap shows the reference would neither collect, trap at a limit, move the collection threshold, nor take a new page or chunk; a list that is full grows inside native code, in a cold path that calls the heap's growth (the capacity, at least twice the old and at least four elements, is the generic append's) and checks the capacity again, with no frame written back and no exit from native code, inlined frames included; anything else runs the reference operation after the frame is written back. An outlined call can enter native code through a per-function cell holding its entry, program, region and frame requirement. The enter helper fills the cell for an ordinary callee whose entry needs no NaN checks on incoming slots. A change of the function program clears its cell. A native chain starting in a nondefault floating-point environment drops cached floating-point entries. The call checks argument widths, native depth and frame capacity. When the arena has room, calls with at most 64 arguments use unrolled initialization for frames of up to 64 slots and compact initialization for frames of 65 to 128 slots. Other frames use the push helper. Value numbering, check elimination and loop-invariant code motion treat the heap checks as ordinary checks, and a read is merged with or moved past only what cannot write it. `--tier-stats` then has a `tier: native heap:` line with the inline and reference allocations and appends and the heap checks the passes removed, by kind.

**Tier 3's registers.** The allocator (`src/jit/regalloc.cpp`) is a linear scan with interval splitting over the machine program. A value that no instruction of a loop reads, which only a frame state (the deoptimization stub) or code after the loop names, does not take a register from where it starts inside that loop: it lives in memory (its frame slot where it has a home) and returns to a register before its next use that needs one, so the loop's registers go to the values it computes with. Where it lives never changes what a run does.

**Tier 3's floats.** Native floating-point arithmetic uses XMM registers. Typed element, field and global loads retain their payload bits in XMM registers, and stores can write directly from them. A binary32 value read from four-byte storage has zero upper bits. A raw eight-byte cell preserves its entire word until an operation defines a new value. Values chosen among several inputs or returned by a helper or call can reach the next float operation through a general register. Each float operation uses the scalar SSE2 instruction `lift::evaluate_float` uses: `addsd`, `subsd`, `mulsd` and `divsd` (the `ss` forms for binary32), `ucomisd` and `ucomiss` with the reference's handling of unordered operands, `cvtsi2sd` with the reference's halving for an unsigned value of 2^63 or more, `cvttsd2si` with the range check (a failure deoptimizes), `cvtss2sd` and `cvtsd2ss` with an explicit NaN test, negation as an exclusive or with the sign bit; never a fused multiply-add, AVX, x87, another rounding, or a change of the floating-point environment. The reference gives the canonical quiet NaN for every NaN result of an addition, subtraction, multiplication or division; native code keeps the hardware's NaN of such a result, which is a NaN exactly where the reference's is and equal to it elsewhere, and replaces it by the canonical NaN only where its bits are observed: before a store to a field, element or global or an append (inline or through the helper), the choice of a selection among values, a call, helper or return argument, an integer operation on the bits (`to_bits`), and a negation or a phi whose result is observed so; comparisons, arithmetic, conversions, hash codes and square roots read any NaN as the reference does. A frame write (a deoptimization, a write-back) canonicalizes such a value in cold code, and a spill of such a value into its frame slot stores the canonical NaN in place of any NaN only where the value is live at a write-back, a helper or a call (the reference code that reads the frame after the write-back); every other spill stores the bits as they are, and the write-back that follows canonicalizes them in the frame slot. A float slot whose value code takes as no NaN but the canonical one where it joins such a result (a parameter or a slot at a loop-head entry) must hold no other NaN when the code is entered; otherwise the entry is refused and the program interpreter runs on. The kernel exit of `neura.math.sqrt` at ABI version 1 (one binary64 argument, a charge of 1 step, a binary64 result) becomes `sqrtsd`, which is the kernel's correctly rounded square root, and its step is counted as a kernel step of native code, so no helper runs for it; `Float64.abs` and `Float32.abs`, once inlined, become an `andpd` with the magnitude mask. Native code that computes floats, or takes a square root, is entered only in the default floating-point environment. The line `tier: native kernel helpers N` counts the kernel exits native programs ran through the helper.

**Frame and entries.** A program's slot registers are the slots of the running frame itself, so a call leaves its caller as tier 1 would, a return finds it so, and the collector sees every slot at every point where it can run. Registers for temporaries, constants, and immediates live in a table the run keeps for each program. The dispatcher enters a program at an **entry**: the function's block 0, the resume block of every exit the program does not follow inside its frame (a call's, a host request's and its error continuation's, a scheduler operation's, a kernel's), and every loop head. Each entry has its own set of slots that some path reads before writing, which must be initialized there, and every initialized slot of the frame must hold a value that fits its type, or the program is not entered. A function with more than 4096 blocks or 65535 slots gets no program, and a function whose block 0 is not lifted, wired, or empty is not formed until it is (the cache waits as it does for a region, then uses regions).

**What a program runs.** Besides what a region runs:

- a **call** to a function (a direct call, an interface call through its dispatch block, a closure call): the block's assignments commit, the call block is one step charged to the caller, and the frame is pushed with the checks and the heap charge of tier 1 (a task image charges the frame's cells). The program then goes on in the callee's program when it has one whose entry checks pass, and otherwise **leaves** so that tier 1 runs the callee. A return goes on in the program the call came from, at the call's resume block, without entry checks; a return from the last frame of a task or a run, from a callback, or out of an open scope is left to tier 1. A dispatch block whose tag matches no case is left to tier 1, which raises the invalid-dispatch trap.
- a **helper**, for every state operation a region does not run: allocation (`AllocateObject`, `AllocateCollection`, `RepeatCollection`), `AppendElement`, `RemoveElement`, `FreeObject`, `ClassHash`, `ClassText`, `ConstructText`, `TextSlice`, `TextFromUtf8`, `ScalarText` of one value, and `Kernel`. The block commits its assignments, is charged its step, and the executor's own state-operation code runs with the arguments read before the commit: the limits, the order in which they are checked, the handles, the heap cells, the collections, and the traps are those of tier 1, because the code is the same. A fault there is the run's trap **in place**: the program ends, the block's step has been charged, the frame's block is the helper's block, and the caller list is the one tier 0 builds, so nothing is run again. A collection inside a helper sees the same frames as tier 1's. A kernel charges steps the checkpoints did not count, so its resume block is a checkpoint.
- any other exit, a host request, a scheduler operation, a trap, or a message trap, is a **deoptimization**: tier 1 runs the block, and the entry at its resume block takes the program up again.

A block that tier 1 does not run lifted, wired, or empty when the program is formed is a **stub**: its code is a deoptimization at the block (after the checkpoint's budget check when the block has one). Formation proves at most 32 hinted blocks that never ran, so that cold blocks are not left out; a program formed while some blocks were still pending is formed again, as a region is (at four times the arrivals, at most four times), and the earlier version stays alive for the frames that return into it.

**Steps and checks.** The blocks a program completes are steps, added to the run's count, to the function of the frame that ran them under `--profile`, and to the task, whenever the program calls, returns, runs a helper, or ends; so the counts at every point where the run can be observed are those of tier 1, and a kernel's steps are charged after its block's. Each entry begins with the check of a checkpoint (against `--max-steps`, the scheduler's quantum, and a fleet's rounds); when it fails the program deoptimizes there and tier 1 runs on a block at a time, so every limit trap and every end of a turn happens at the block, with the counts, of tier 0. `NEURA_TIER_CHECK=1` compiles calls, returns, dispatches, and helpers as deoptimizations, since its check cannot follow a run into another frame. `NEURA_TIER_CHECK=2` compares a run with programs as it compares one with regions, and gives a program an allowance of 65,536 blocks between two comparisons, so a long loop is compared as it runs and not only at its end.

`--tier-stats` prints a line `tier: programs P (B blocks, S stubs, E entries); calls C, returns R, helpers H, traps in place T; steps in programs N` once a program has formed, and a line `tier: no program N: reason` for each reason a function got none. The count of steps run "in regions" includes the steps of programs.

#### Native compilation

The native code generator (`src/jit`) compiles a region program to machine code, which runs in place of the region interpreter. It is part of tier 2: below `--tier=2` nothing is compiled. A region is compiled once, synchronously, by the first run that enters it with native code enabled; every run that shares the tier cache shares the code. Nothing depends on timing: there is no background thread, and whether a region runs compiled changes only its speed.

**What is compiled inline.** Moves, masks, gathers, stores with their initialized flags, branches, switches (an invalid selector deoptimizes), jumps, the step count of completed blocks, budget checks, leaves, and deoptimizations; and the lowered integer operations of 1 to 64 bits: addition, subtraction, negation, and multiplication with their overflow checks, division and remainder (a zero divisor fails), comparisons, boolean and bitwise operations, shifts (a count of at least the width fails), index checks, and integer conversions. Each is compiled from the expression `lift::evaluate` uses (`src/lift/evaluate.hpp`), for every 64-bit operand value: the same masks, the same sign extension, the same failure conditions. Where a condition is exactly the processor's carry or signed-overflow flag (a 64-bit addition, subtraction, or multiplication), the check branches on that flag to a deoptimization stub. The float operations of binary32 and binary64 are compiled inline too: addition, subtraction, multiplication, division, negation, comparisons, conversion between the two formats, and conversions to and from integers of 1 to 64 bits. Each follows `lift::evaluate_float` (`src/lift/lowered_block.cpp`) with the processor's own scalar instruction (SSE2 on x86-64, scalar floating point on AArch64; never a fused multiply-add, AVX, or x87): it reads a binary32 operand from the low 32 bits of its register and zero-extends a binary32 result, replaces every NaN result with the canonical quiet NaN, negates by flipping the sign bit (a NaN keeps its payload), compares unordered operands as the reference does, converts an unsigned integer of 2^63 or more by the reference's halving with a sticky bit, and checks a truncation against the integer range of its width. A truncation that is NaN or outside the signed 64-bit range calls the helper. The code relies on the default floating-point environment, which the entry rule guarantees, and never changes it. An operation writes its register only after its checks pass, so a deoptimization finds every slot register as the block was entered.

**What calls helpers.** Signed division and remainder by -1, float operations of the 16-bit formats, a float truncation outside the signed 64-bit range, and instructions of other widths call `lift::evaluate` itself, the interpreter's code, so they are bit-exact with it by construction. A region that computes floats is not entered at all in a floating-point environment other than the default (the entry rule above). A reference check, an inline state operation, and a poll call the executor's own code, with the same arguments, checks, traps, and trap texts. Helpers are reached through a table in the context the code receives; the code contains no address of the executable, so it works in the static launcher too. A helper that catches an exception other than a trap returns to the code, which returns at once; the executor then rethrows it where the interpreter's would have left the region.

**Registers.** Region registers live in the executor's register array. The registers the program uses most are kept in machine registers for the whole program (7 on x86-64, 13 on AArch64): they are loaded at entry, and stored before every helper call that may read them or clobber them and at every exit. Deoptimization, leaving, and the exception return all pass through one exit that stores them, so the write-backs, initialized flags, completed steps, and the block reached are exactly the interpreter's.

**Memory.** Code is written into a private read-write mapping that is then made read-execute (`mmap`, then `mprotect`) and never written again: no mapping is writable and executable at once. On Linux AArch64 the instruction cache is cleared before the mapping becomes executable. On Apple silicon the mapping is a `MAP_JIT` mapping, which the writing thread switches between writable and executable with `pthread_jit_write_protect_np`, followed by `sys_icache_invalidate`; a macOS executable signed with the hardened runtime needs the `com.apple.security.cs.allow-jit` entitlement for that ([Code signing](../CodeSigning.md)). A region whose code cannot be generated (for example a branch beyond an AArch64 branch's range) or mapped runs on the interpreter, and `--tier-stats` counts it with the reason.

**Why it is not observable.** The generated code performs the region program's ops in program order with the interpreter's semantics, and everything outside the ops (the entry checks, the constant loads, the write-back, the step, profile, and task counts, the statistics) is the executor's code, shared with the interpreter. `NEURA_TIER_CHECK=1` checks native regions against tier 1 exactly as it checks interpreted ones, and `NEURA_TIER_CHECK=2` checks whole runs, native code included, against a shadow run at tier 1 (below).

**Platforms.** `--jit=auto`, the default, enables native code only where its generated code has been run and checked:

| Platform | `auto` | `on` | Verified |
| --- | --- | --- | --- |
| x86-64 Linux | native code | native code | by execution: unit tests, the tier 2 suite, and byte-for-byte runtime identity against tier 0 |
| AArch64 Linux | interpreter | native code (experimental) | encodings against an assembler's, and generation of the unit-test programs; not by execution |
| AArch64 macOS | interpreter | native code (experimental) | as AArch64 Linux; the `MAP_JIT` path is not run |
| x86-64 macOS | interpreter | native code (experimental) | the x86-64 code generator as on Linux; the macOS mapping path is not run |
| Windows x86-64 | interpreter | `Windows has no JIT in 0.3.0` | Win64 JIT deferred |
| Other processors and systems | interpreter | an error | no code generator |

`--jit=on` starts by running a small generated program; when it cannot be mapped or does not run as generated, or there is no code generator for the processor and system, the run fails before it starts. `auto` uses the interpreter in those cases, silently. A CI job definition (`.github/workflows/jit.yml`) runs the identity comparison with `--jit=on` on AArch64 Linux and macOS runners, so `auto` can be extended once it passes there.

Native code is not the [native capability](../lang/Tooling.md#build-and-run-executables): `--deny-native` governs C code a program calls through `import:c` and `Std.DynamicForeign`, and does not turn the code generator off. Parallel items, which run on worker threads, share the cache's code: published code is immutable, and each run keeps its own context and registers.

#### Controls

- `--tier=0|1|2` on `neura run` and `neura test` (`RunLimits::tier`) sets the highest tier; 2 is the default. Tiers 1 and 2 are not used with a graph device, which evaluates the graphs it accepts. A fleet's members share the command's tier cache and use it once the fleet drops a device that declines every job, as auto mode's device does after it gives up ([GPU execution](../lang/GpuExecution.md#105-advance)).
- `NEURA_TIER=0` or `NEURA_TIER=1` in the environment lowers the tier of every run in the process, the test suite's included. `NEURA_RUN_OPTIONS` may lower the tier of a [native executable](../lang/Standalone.md) with `--tier=0` or `--tier=1`. Nothing raises it.
- `--jit=off|on|auto` on `neura run` and `neura test` (`RunLimits::jit`) chooses between native code and the interpreter for regions (above); `auto` is the default. `NEURA_JIT=off|on|auto` in the environment applies to every run in the process, the test suite's included, and combines with the option: `off` from either wins, then `on` from either. `NEURA_RUN_OPTIONS` accepts `--jit` for a native executable. `NEURA_JIT_DUMP=1` writes each compiled region's code, in hexadecimal, to standard error (or to the file it names).
- `--tier-stats` prints, after the run, the blocks lifted (by hint and by search), the proof and search time, the steps each tier ran (tier 2 counts the steps run inside regions), with the steps kernel calls charged for themselves (`kernel calls N`, shown only when there are some) so that the total is the run's `--stats` step count, why blocks stayed on tier 0, the blocks that ran most steps on tier 0, the regions formed, how often regions were entered, left, and deoptimized and why, the blocks where they deoptimized and left most, and for native code the mode, the regions compiled and their bytes of code, the regions left on the interpreter and why, and how many entries ran native code. These lines are diagnostics, not part of the invariants above: they depend on timing and threads. `--stats` is unchanged, so its output is identical at every tier.
- The last line of `--tier-stats` divides the wall time of the command among what the runtime was doing, in milliseconds: `tier: time: total T ms: load L, proving P, searching S, tier 0 Z, tier 1 D, regions R, collection C, host H, other O`. The total runs from a clock reading before the image is read (for `neura test`, before its built image is loaded; for a native executable, when the runner starts the run, after the image has been decoded) to one after the other statistics are printed. *Load* is reading, decoding, and validating the image and setting up each execution, up to its first step. *Proving* and *searching* are the time tier 1 spent proving hints and searching for forms on the run's thread, as measured for the first line, and are not counted again in tier 0 or tier 1. *Tier 0* is steps evaluated by reference, declined lifted steps included. *Tier 1* is lifted, wired, and empty steps with the commits of their exits (calls, returns, state operations), and forming regions and compiling them to native code, which has no category of its own. *Regions* is the time inside tier 2 regions, interpreted or native, with their helpers. *Collection* is garbage collection, wherever it was triggered. *Host* runs from a host request, poll, or wait leaving the execution to the execution's next step: the service, console output, file and network I/O, waiting for completions, and applying them; a callback's steps count as steps. *Other* is the total less every other category (scheduling decisions, the runner's work between and after runs, the statistics), clamped at zero. Every moment belongs to one category, so the figures sum to the total within rounding. The steady clock is read only when the category changes (a region's entry, a step at another tier than the step before, a collection, a host request, a scheduling decision), never per step, and nothing depends on the times; without `--tier-stats` nothing is timed. Each change of category costs one clock reading, so a program that enters regions millions of times runs measurably slower with the option than without it (about a fifth slower for `tests/bench-wall/neura/binary-trees.nra`), and the readings' own time is counted in the categories they separate. `run --each` and `neura test` time their executions, which run one after another, on one timeline, and parallel items evaluated in order belong to their run's. With a graph device, a fleet included, or more than one parallel worker, whose threads' time overlaps the run's, the line is omitted.
- `NEURA_TIER_CHECK=1` evaluates every block that tier 1 runs by reference as well, and runs every region execution again at tier 1: the region runs, everything it changed is put back (slots and their flags, the block, the step, per-function, task, and poll counts, and each write to heap or global storage, from a log), the same blocks run at tier 1, and the two must agree on the block reached, every slot and flag of the frame, the counts, and the writes to storage, in order and with their values. Reads are covered by the slots they feed. It aborts the process with a report on any difference. It is a debugging aid. Under it the `tier: steps` line of `--tier-stats` counts the executions the check repeats as well, and so exceeds the step count of `--stats`.
- `NEURA_TIER_CHECK=2` runs every execution that would run above tier 1 beside a **shadow**: a second execution of the same image, arguments, limits, and initial state, restricted to tier 1 (no regions, no native code, no check of its own). The run itself runs as in production, regions and native code included; the region check of `NEURA_TIER_CHECK=1` is not used. The shadow shares the image and the tier cache's lowered blocks, which are immutable once published; its counts of block executions join the run's, which changes only when blocks are lifted. It has its own heap, frames, globals, scheduler, and counters, and no host services, observer, task dump, or timeline: it makes no host request, writes nothing, and loads no native library. The two are compared at every return of compiled code to the dispatcher, at every event the run hands to its caller (a host request, poll, wait, cancel, completion, or trap), and after each callback a host service makes. The shadow first runs, step by step, to the run's step count; an event before it, or a step past it, is a difference. Then, in this order: the step count; whether each has finished or trapped, and a trap's kind, reason, detail text, function, block, and callers; the event, and for a host request its import and every argument; the frames, from the bottom, each with its function, block, return slot and block, and every slot's initialized flag and, when it is initialized, its value; every global and its flag; the last handle, live and peak heap cells, and the collection threshold; the steps of each function under `--profile`; in an image with tasks, every field of the scheduler: every task (its state, frames, scopes, select arms, parked operation, and counters), the runnable queue, the scheduler's counters and next identities, every scope record, channel (its buffer and its queues of senders and receivers, in order), timer and guard (with their queues of waiters), armed deadline, pending request, and cancellation, and the totals of released tasks by spawn site; and the host requests issued, identity numbers given, the request the run waits for, the parallel items outstanding, and the constants. The tier machinery (block plans, tier counts and statistics, region registers), scratch buffers that each step overwrites before reading, and caches built from the image are not compared: they differ between the run and its shadow by design and decide only how a block is evaluated. At the end of the run, at every one of these points under `NEURA_TIER_CHECK_HEAP=1`, and otherwise at a point where at least 64 points and at least 2 steps for each live heap entry found at the last such comparison have passed since it, the heaps are compared too, entry by entry in handle order: presence, kind, type, cells and their initialized flags, bytes, list version, and identity number. The bits of an uninitialized slot, field, or global cannot be read, and are not compared. The first difference aborts the process with a report on standard error: `neura: NEURA_TIER_CHECK: the shadow run differs at step N`, where compiled code was last entered, the last sync point, where the run is, the item, and its value in each. What enters the run from outside is given to the shadow after the run has taken it, through the same calls of `nvm::Execution`: completions, deliveries, clock readings, and callbacks, whose own host requests the shadow makes against the run's recorded completions. Parallel items evaluated in order each have a shadow. A run with a graph device, a schedule chooser (`neura test --schedules` and `--schedule`), more than one parallel worker, as a member of a fleet, or under `--replay` is not checked (a run under `--record` is checked); it says so in one line on standard error, `neura: NEURA_TIER_CHECK=2 is not applied:` and why, once per process for each reason, and runs as it would without the variable. Without the variable, nothing of this runs. It is a debugging aid, and a checked run is several times slower.
- `NEURA_TIER_EAGER=1` lifts every block the first time it runs, with ample proof work and search time, and forms every region at its first arrival, so that short runs exercise tiers 1 and 2; it too changes only which blocks run lifted or in regions, and when. `NEURA_TIER_DUMP=1` prints each region program as it is formed.
- `NEURA_TIER3` chooses how function programs run. Unset, tier 3 is native where native code is available (x86-64 Linux, `--jit` and `NEURA_JIT` not `off`) and off elsewhere, so a run without native code is the run of a build without tier 3. `off` (and any value not named here) turns tier 3 off everywhere: no function program is formed (unless `NEURA_TIER_PROGRAMS=1` forms them for the interpreter), and the run is what it was before tier 3 existed: the same output, steps, traps and `--tier-stats` lines, except that the `tier: steps` line now counts kernel calls (below). `native` runs function programs as tier 3 native programs in machine code on x86-64 Linux, and on the IR interpreter elsewhere (with a reason in `--tier-stats`); `interp` runs them on the IR interpreter; both force function programs to form whatever `NEURA_TIER_PROGRAMS` says. It changes only how programs run, and `--tier-stats` then has a `tier: native programs` line (also by default where tier 3 is native). `NEURA_TIER3_VERIFY=1` verifies the IR of each native program as it is built (always in a debug build); a violation prints the rule and the IR and aborts. `NEURA_TIER3_PASSES=0` turns tier 3's passes off, to compare a run with and without them. `NEURA_TIER3_AFTER=N` lifts blocks and forms programs as `NEURA_TIER_EAGER=1` does but turns a program native at its Nth checkpoint arrival, so that a loop is handed to native code in its middle; both are testing aids and change nothing a run does. `NEURA_TIER_DUMP=1` also prints the IR of each native program built or refused.
- `NEURA_TIER_PROGRAMS=1` forms [function programs](#tier-2-function-programs) in place of regions, on the interpreter; it changes only which blocks run in programs and when, like `NEURA_TIER_EAGER=1`. `NEURA_TIER_DUMP=1` then prints each function program as it is formed.

- The readers of `NEURA_TIER`, `NEURA_TIER_CHECK`, `NEURA_TIER_CHECK_HEAP`, `NEURA_TIER_EAGER`, `NEURA_TIER_PROGRAMS`, `NEURA_TIER3`, `NEURA_TIER3_AFTER`, `NEURA_TIER3_PASSES`, `NEURA_TIER3_VERIFY` and `NEURA_JIT` keep their first answer for the life of the process. A worker of the [runtime service](Service.md), which is started before it knows its application, replaces its environment with the caller's before any of them runs, and a reader that runs while the environment is still held aborts the worker (`src/nvm/environment.cpp`). Every other process starts with its environment bound, so for a direct run nothing changes.

#### Why the result does not depend on the tier

A lifted block is used only when the structural proof shows that the graph is the circuit library's construction of its typed operations, and the overflow proof shows that reference evaluation of that graph neither overflows nor yields an output lane other than 0 or 1 for any input. The lowering computes each of those operations exactly, with the circuits' failure conditions, so its exit and values equal those the reference evaluator would produce, lane for lane, and the reference evaluator could not have trapped. Everything around the evaluation (charging, input checks, the commit, every state operation and host interaction) is the reference code. Which blocks happen to be lifted, and when, depends on thresholds, time budgets, and thread timing, but it can change only the speed of a run.

A region runs blocks that tier 1 would run lifted, wired, or empty, computes each with the same operations, and commits each exit as the reference commit does: values against the state before the block, assignments in parallel, the state operation with the reference code. What it does differently is not observable: it keeps slots in registers between blocks but writes them back before anything else could read them, since the region allocates nothing, calls nothing, and makes no request; it adds steps in bulk, but the budget check keeps every limit, quantum, and fleet round out of reach until tier 1 runs; and anything that fails, or any exit it does not take, puts the frame back to the block's entry state for tier 1 to run the block exactly as it would have. Which regions exist, and when, depends on counts and on what tier 1 has proven, so it too changes only the speed of a run. Native code is the same region program, compiled op for op with the interpreter's semantics and the interpreter's helpers for the rest, so it changes only the speed too.

#### Checking the claim with generated programs

`scripts/program-fuzz.py` checks it on programs nobody wrote by hand. `generate --seed N --out DIR` writes a valid Neura program that is a pure function of `N`: several functions that mix checked integer arithmetic at every width near its bounds, loops, direct and mutual recursion, classes (a field read before it is written on some paths, `destroy` followed by a use on some paths), interfaces, closures, arrays and lists, text, a kernel call, floats with NaN, NaNs with payloads of both formats through arithmetic, negation, abs, stores, calls, `to_bits` and square roots, and for some seeds tasks and a channel. The program takes its size and a fault mask from its arguments and ends with a checksum; each bit of the mask turns on one failure path, so the run ends in that trap after the work before it.

`run --neura BIN --seeds A..B` builds each program once and runs it at `--tier=0` for the reference. It compares the exit status, standard output, standard error (which holds `--stats` and `--profile`), against every mode: `--jit=off` and `--jit=on`, each with `NEURA_TIER_EAGER=1` and without, each with `NEURA_TIER_PROGRAMS=1` and without, `NEURA_TIER_EAGER=1 NEURA_TIER_CHECK=2 NEURA_TIER_PROGRAMS=1`, and `NEURA_TIER3=interp NEURA_TIER_EAGER=1 NEURA_TIER3_VERIFY=1` with and without `NEURA_TIER_CHECK=2`, with `NEURA_TIER3_PASSES=0`, and `NEURA_TIER3=interp NEURA_TIER3_AFTER=7 NEURA_TIER3_VERIFY=1`, the last also without `--profile`, against a reference without it, so that native programs inline calls, and `NEURA_TIER3=interp NEURA_TIER_EAGER=1 NEURA_TIER_CHECK=1`, whose region check runs tier 3's checkable programs (their writes go through the reference state operations); each of these tier 3 modes runs again with `NEURA_TIER3=native` in place of `interp`. Every run sets `NEURA_GPU=off`, so that the compiled tiers, and not a graph device, are what is compared. It then repeats the comparison under limit sweeps chosen so that a step, heap, stack, or frame limit trap lands on every block, and with it a deoptimization or a trap in place: `--max-steps` at every value up to the run's steps when they number at most 2000, otherwise the first 200, the last 200, and 100 values between; `--max-heap-cells` from the smallest value that admits the first allocation to the peak plus 2; `--max-stack-cells` from one to the stack peak plus 2; `--max-frames` from 1 to the deepest call depth plus 2; and `--task-quantum` 1 to 4 for programs with tasks. A difference is written to `--report DIR` with the program, both outputs, and `reproduce.sh`, and the run exits with status 1. `--coarse N` divides the number of points of each sweep by `N`; `--quick`, which the CTest entry `program-fuzz` runs, is three seeds at `--coarse 40`. `compile --seeds A..B` checks that every seed compiles without a diagnostic, and `coverage --seeds A..B` reports how many programs use each feature.

`scripts/runtime-identity.py capture --extended` also captures seeds 1 to 40, so that a capture in each mode compares with a capture at tier 0 like its other cases.

## Execution state

Each run owns its call stack, heap, argument values, pending continuation, resource counters, and host bindings. Starting a fresh run creates fresh state from the image and the launch inputs. The root frame receives the UTF-8 argument array. A function frame has typed slots for parameters, locals, and temporaries. Parameters are initialized on entry and remaining slots begin uninitialized. Reading an uninitialized slot traps. The implementation may use a faster internal layout if the observable behavior is identical.

A normal block transition proceeds in this order:

1. Resolve graph inputs from the current frame and constant pool. Check types, initialization, and applicable limits.
2. Evaluate the graph and decode the selector.
3. Resolve the selected exit's values and slot assignments from the pre-transition frame, constants, and graph outputs. Check the exit, payload types, and destinations.
4. Commit the exit's slot assignments in parallel. Perform the exit action. A call, heap request, or host request records its continuation before control transfers.
5. Enter the destination block, return to the caller, or finish execution.

The parallel assignment rule lets a block swap two slots without an ordering dependency. Exit descriptors for unselected paths have no effects. For short-circuit expressions, the right operand's block is reached only when the left operand selects it. Compiling pure alternatives into a single data-selection graph is valid when the source contract permits both computations to be evaluated.

| Exit | NVM action |
| --- | --- |
| Continue | Enter the given block in the current function. |
| Call | Push a frame with the resolved arguments and enter the selected function. The caller retains the resume block and result slot. |
| Return | Pop the frame, place the result in the caller's result slot if present, and enter the caller's resume block. Returning from the entry frame completes the run. |
| State operation | Perform the specified checked heap or global storage operation, or call a built-in kernel ([Kernel calls](#kernel-calls)), store its result if present, and enter the resume block. |
| Host call | Invoke the bound service with the resolved arguments and resume on the declared success or failure continuation. |
| Trap | Terminate the run with the specified runtime fault. |

Direct calls name a function in execution metadata. Dynamic dispatch reads the receiver's type tag and uses a graph-selected exit to choose a compatible function. NVM checks the handle and call signature at the boundary. A graph can implement selection as a decision tree across blocks when a single graph would make the dispatch unnecessarily large.

## Fleets

A fleet advances independent executions of one image. Each member owns its frames, globals, heap, limits, and counters. A round considers a bounded window of unfinished members and may evaluate their graphs together. Only the lowest-numbered member whose final event is still unreported can issue a host request. The caller completes that request or serves a callback before the member continues. Final events arrive in member order. The resulting host requests, responses, and final events follow the same order as running the members one at a time.

The head can always start. Other members can start while the sum of the live heap cells of started, unfinished members is below one member’s heap limit. Admission counts initial constants and arguments as soon as a member starts, including before its first graph step. Once admitted, a member keeps running under its own limits. Aggregate process memory can exceed the limit of one member.

When no device is set and every member has been admitted, the reference executor can group rounds until the head reaches its next event. Other runnable members advance through the same number of rounds, stopping at their first event. Each member sees the same inputs and state, and no admission or host response can intervene during the group. The visible events and round count remain those of the individual rounds.

Fleet admission tracks live heap cells as they change. Finishing a member removes its remaining cells from the total before another member is admitted. With a graph device, the fleet checks graph input reads before placement and can defer packing their lanes until evaluation. The begun frame and constants stay unchanged in between. An automatic device can request full jobs only for the graph indices it selects. Other devices receive the eager batch, and every declined step uses the reference evaluator.

## Heap and objects

Objects have a runtime type tag, a layout ID, and typed field slots. Layouts preserve inherited fields at stable indices. A method receives the object handle as an explicit argument. Each object has independent storage, while calls share the compiled method graphs. Collections use typed element slots, and lengths and indices are checked before accessing storage.

Object and interface references can carry nil as handle zero. The collector skips it, and field access, virtual dispatch, and destruction fault when they try to dereference it. A type test returns false for nil, and a checked cast preserves it. Class identity operations give a live object a sequence number when its default hash or text is first requested. The number stays with the object and depends on request order.

An allocation creates a fresh handle and uninitialized fields. Compiler-generated constructor control flow performs base initialization, field initialization, and the declared constructor body in language order. It exposes the result of `new` on successful completion. If the language permits a field to be initialized later, its slot remains uninitialized until a store. A premature load traps. Field and collection stores validate the handle, layout, index, and value type before changing storage. Compiler-generated destruction calls the required cleanup methods and then invalidates the handle. Freed handles cannot name later allocations. These rules define runtime checks. The language specification defines which source operations are legal and the ordering of language-visible initialization and cleanup.

For example, incrementing a counter runs a block that requests a field read, a graph that adds to the returned value, and a block that requests a field write. The heap handler performs the read and write. The graph supplies the new value.

Each entry is one block that starts with a fixed header: its kind, type, mark, and count of fields, elements, or bytes. An object's block holds a bit per field that says whether it is initialized, then the fields at eight bytes each. An array's elements, and the bytes of text and bytes, follow the header inline. A list's header points to a separate buffer that grows geometrically, so appending and removing never move the header. An array or list stores its elements at the width its element type declares: one byte for `bool` and 8-bit scalars, two, four, or eight bytes for wider scalars, and eight bytes for references. A store of a value with a bit above that width first converts that collection to eight-byte elements, once, so every element still reads back the bits stored. Blocks come from size classes that a run reuses after a collection frees them. None of this is observable: outputs, traps, `steps`, and `peak_heap_cells`, which counts one cell per entry, field, element, or byte whatever the storage, are the same as for any other storage. An array or list of aggregates (NVR 1.7) is stored one eight-byte word per component, element after element, and counts one cell per word: its entry costs `1 + length * k` cells for `k` components, an append adds `k` and a removal returns `k`, and `length` reports elements, not words. `src/nvm/heap.hpp` publishes the layout for native code.

### Managed list runs

The append-run state operation (NVR 1.10) starts where an element-wise loop would append its current element. It takes the destination list, the current signed 32-bit loop index, the exclusive end, and the evaluated element words. The byte forms also take a source list or text. Its result replaces the current index before the original increment. For the four-byte loop the index identifies the first byte of the last group, and the operation starts at that group's final append. The original loop test and element read take place before the operation.

The current block pays for its append. Each additional iteration charges the original increment, test, reads, and append steps. A repeat charges three steps per additional element. A byte range charges four, or five when the loop also reads the builder's backing-list field. The four-byte loop charges ten steps per additional group and batches only complete groups. Any growth accounts for one heap cell per element word. Each successful append increments the structural version once, modulo 2^64, including when all the elements hold the same reference or aggregate. A list created empty and filled with `n` elements has version `n`.

A range reads in ascending index order. If the source and destination are the same list, reads can see bytes appended by earlier iterations. The runtime can copy a range in one batch when it lies wholly in the existing source prefix. A run can skip only iterations whose accesses, capacity, step limit, and collection threshold allow the same commits as the original loop. At a possible bound or budget failure, a collector safepoint, or a scheduling or observation boundary, it takes the ordinary single-element append path or stops the batch before that boundary. The continuation then executes the original order of checks, with the same successful prefix and version if a check fails. Region lists use the ordinary stack-cell growth path. The same operation handles list growth in every execution tier.

### Garbage collection

NVM uses a non-moving tracing collector. The root set comprises reference constants, initialized reference globals, and initialized reference slots in every active frame. Temporary references also remain rooted while constructing the launch arguments, allocating a collection from its already evaluated elements, or appending an element after the exit's parallel assignments. NVM traces initialized reference fields by the object's actual layout and visits reference elements in arrays and lists; in an array or list of aggregates (NVR 1.7) it visits, in every element, the components whose type is a reference. Text and byte storage are leaves. Numeric slots never keep an object alive even when their bits match its handle.

Allocation and list growth are safepoints. The collector marks reachable entries iteratively and sweeps the remaining entries, including unreachable cycles. It attempts collection before an allocation or growth would exceed the configured heap limit. It also collects at a soft threshold that grows with the retained heap, so workloads that release objects can reclaim space before reaching the hard limit. Collection does not consume program steps and uses no clocks or background threads. An initialized frame slot retains its reference until the slot is overwritten or its frame returns.

The collector caches the reference positions in each encountered object layout, aggregate layout, and frame signature. Subsequent traces visit those positions directly and skip scalar cells.

Collection reclaims storage without invoking language cleanup methods. An explicit `destroy` runs its compiled cleanup and invalidates the object immediately. Both reclaimed and explicitly destroyed handles remain invalid, and every new allocation receives a fresh handle. The run's handle limit counts all assigned handles independently of reclaimed storage. Programs must keep references in typed storage across safepoints to retain their targets.

### Storage regions

NVR 1.7 regions ([NVR](NVR.md#storage-regions-17)) give an activation entries that it frees itself, by release or when it ends, instead of leaving them to the collector.

- **Where they live.** The running task's open regions are a stack kept beside its frames (`FrameStack::regions`, in `src/nvm/machine.cpp`), outermost first. Each region records its token, the frame depth at which it was entered, and the handles of the entries it owns in ascending order, which is creation order. The stack is not in a frame header, which native code indexes, and it moves with the frames when a task parks and resumes. Entries carry a flag in their header (`Heap::region_entry_flag()`) that native code reads. Tokens come from a counter of the run; a token is looked up only in the running task's stack, so another task's token finds nothing.
- **Where they are released.** At `release-region`; when a frame is popped by a return, every region it entered and did not release; at the end of the run, on a trap or a completion, every region of every task; and when a task finishes. Tier 2 and tier 3 release at the same points: a function program's return, and tier 3's return helper, release every region the frame entered before popping it; machine code pops a frame in place only for a function with no `enter-region` exit in any block, lifted or not (`tier3::Function::enters_region`), so every frame that can own a region returns through the helper. A deoptimization changes no region: the region operations run as helpers on the frames tier 1 has, never inside an inlined callee (a function that has one is not inlined, and the verifier's rule V11 checks it under `NEURA_TIER3_VERIFY=1`), so the frames a deoptimization writes back or materializes own exactly the regions they own at tier 0. A trap releases every region at its end, so a run's live stack cells are zero after it, except for a debugger launch, which keeps the entries of a trap for inspection until the execution is freed. Released handles are kept as intervals, so a later access traps `released storage accessed` rather than `invalid reference handle`, whatever the tier: a lookup that finds no entry always ends at the reference path's check.
- **Accounting.** Region cells count as stack cells, in `RunResult::peak_stack_cells`, and are limited by `RunLimits::max_stack_cells` (`--max-stack-cells`, 2^24 by default; it also applies to the items of a parallel map). They are not heap cells: they are not in `peak_heap_cells`, the collection threshold, a fleet's admission, or `--max-heap-cells`. A task's frames still count as heap cells as before. `neura run --stats` and `neura test --stats` print `peak stack cells` only for an image that uses a region operation, so every other image prints what it printed before, and the JSON events of `neura test --reporter=json` carry `peakStackCells` for such an image only.
- **Tiers.** A region operation is a helper of a function program in tiers 2 and 3, which runs the reference operation, and an exit that a region of tier 2 does not take (see Execution tiers), so the result, the steps, and both peaks are those of tier 0 in every mode. Field and element accesses to a region entry are ordinary heap accesses in every tier; a released entry has no handle, so an inline lookup fails, the block runs again at tier 1, and it traps as tier 0 does. The shadow oracle compares each task's region stack (tokens, owning frame depths and entries), the region flag of each heap entry, the live and peak stack cells, the token counter and the released handles.
- **Static storage.** The reserved token names a shared execution-lifetime region. The collector visits entries in that region, and execution teardown releases them. Noncapturing callable descriptors are region roots initialized from the image's constant table.
- **Task images.** A spawned task's regions are its own: they begin empty, end with the task, and are released when it finishes. A token is not transferable.
- **Limits and tools.** `neura run`, `neura run --each`, `neura test`, the C++ `RunLimits`, the items of a parallel map, and the debugger launch (`maxStackCells`) take the limit; a native executable accepts `--max-stack-cells` in `NEURA_RUN_OPTIONS` to lower it, and its container records no stack limit, so it has the default. A recorded trace reproduces a region trap: its kind is in the trace file.

### Class hook events

NVR 1.8 class hook operations ([NVR](NVR.md#class-hooks-18)) keep, per task, the stack of events that are open (`FrameStack::hooks`, in `src/nvm/machine.cpp`), beside the frames like the regions. Each entry is the kind, the policy word, the reference and the frame depth that opened it; `hook-enter` traps on an equal entry (`class hook recursion`) or a 65th (`class hook nesting limit exceeded`), and `hook-leave`, a return, and a scheduler exit check that the frame's events are balanced (`invalid class hook operation`). A trap or the end of a run empties the stack. The operations are exits that no region or program takes: a block with one runs at tier 1 or the interpreter, a function with `hook-enter` keeps its returns there, and the inline returns of tiers 2 and 3 fall back to it when an event of the frame is open. The result, the steps, and the peaks are those of tier 0 in every mode. A debugger stop, an inspection and an evaluation call neither operation. The compiler supplies the concrete policy name as a constant so that stripped images preserve the recursion diagnostic. A setter's consecutive state write validates the whole destination before committing either word. A trap retains the old handle, nil policy and initialized state for a debugger inspecting the stopped execution.

## Host calls and standard output

A host import declares a service name, interface version, typed arguments, and typed success and error results. An exit references an import by table index. At load time the runtime binds each declared import to a registered service with the same signature and version under the runner's service policy. Imports grant access only to their bound service. A service that needs filesystem or network access defines that authority in its own interface and configuration.

A request contains the import, resolved arguments, and an execution-local sequence number. NVM issues the request once on entering the selected exit. A completion supplies either the success or error value. The runtime type-checks that value, writes the designated result slot, and enters the corresponding resume block. A suspended run keeps the pending request and resumes from its completion. The execution contract covers a live run. Durable recovery across a process crash requires a separate persistence protocol.

Host services receive copied values. Booleans, integers, and floating-point values keep their slot bit encodings. Strings, byte arrays, and byte lists use byte sequences. Other arrays and lists transfer their elements in index order, and tuples transfer their fields in declaration order. Host signatures describe these shapes recursively without image-local type indices. The runner limits copied elements and bytes using the heap-cell budget and bounds the nesting depth. Handles remain inside NVM, and a compound completion allocates fresh VM storage with its partially constructed values rooted until completion.

A terminal completion from `neura.process.exit` version 1 ends only the current NVM execution with the supplied status from 0 through 255. A recorder stores that completion and replay returns the same terminal result without invoking the service. The runner must register the service before an image can call it.

The standard console service is `neura.console.write_line` version 1. It takes a UTF-8 string and returns either success with no payload or an unsigned 32-bit error code. Error code 1 denotes a failed write. It emits the string's bytes followed by a single LF byte, independent of platform newline conventions. A host write can partially succeed before reporting failure. The runtime reports the failure without retrying. The language library determines how that result appears to source code.

The providers retry nonblocking calls on readiness and keep request-owned descriptor references until completion. `Std.Net.Socket.Internal.HostCalls` binds these services for the public socket types.

On Windows, Winsock TCP listeners and UDP sockets bound to the IPv6 wildcard `::` also accept IPv4 traffic. Windows supports Unix-domain stream sockets at UTF-8 paths. Unix-domain datagrams, the abstract namespace and explicit pipes need a host implementation. Multipath TCP asks the host for protocol 262 and answers 13 (`Unsupported`) when it is unavailable. See the [Windows socket decision](../design/Windows030.md#w14-sockets-and-readiness) for option mappings.

**QUIC services.** The `neura.net.quic.*` services after `dns_exchange` run general QUIC on the TLS build's OpenSSL 4.1 QUIC stack, and answer 13 (`Unsupported`) in a build without it. Every call needs the network capability. The provider holds every endpoint, connection and stream; an ID it no longer holds answers 1 (`NotFound`), which the library reports as a closed handle. An ID carries a generation, so the ID of a closed object never reaches a later one that reuses its slot. At most one operation per direction may be pending: one `accept` per endpoint, one `accept_stream` per connection, and one read and one write per stream; another answers 17 (`Busy`) at once and is never queued. Waiting calls overlap and are cancellable. Each waits on its UDP socket in the direction OpenSSL asks for, wakes at OpenSSL's next timer (`PendingOperation::wake_at`), and is also attempted when OpenSSL already reports what it waits for, since another operation or the background work may have processed the datagram that made it ready. Live endpoints and connections are serviced as background work on every driver check. The provider never offers early data: in a probe of the pinned stack, configuring a server for early data made every session resumption fail.

**TLS services.** Builds with the TLS provider link OpenSSL 4.1 and offer TLS 1.2 and 1.3. On Windows the provider uses Winsock and the Windows `ROOT` store. On other targets it uses OpenSSL's system trust paths. Every call needs the network capability. A caller-supplied PEM file needs the file capability. The provider checks that the path names a regular file before opening it. With path prefixes, it resolves the path and checks it against the prefixes before opening, checks the opened handle's own path against the prefixes again, and loads the contents through that handle. On Linux it first opens the resolved name as an `O_PATH` handle, which names the file without opening it, through `openat2` with `RESOLVE_NO_SYMLINKS`, so a directory swapped for a link after the check makes the open fail instead of following it. It checks that handle's kind and path, and only then opens the same file for reading through `/proc/self/fd`. Under path prefixes on Linux a FIFO or device is therefore never opened, and a file outside the prefixes is never opened for reading. Where `openat2` is missing (before Linux 5.6, or refused by a seccomp filter) the `O_PATH` open follows a swapped directory, and the handle check rejects where it leads before anything is opened for reading. On other systems the provider checks the kind of the resolved name and opens it with `O_NOFOLLOW` (and `O_NOFOLLOW_ANY` on macOS), so only the final component cannot be a link: a directory swapped between the check and the open can still make the open reach a FIFO or device outside the prefixes, which the handle check then rejects after it was opened, without blocking because the open is nonblocking. Without prefixes the same check-then-open race applies on every system. Path checks cannot detect a hard link: a hard link inside a prefix to a file outside it is that file's name inside the prefix, so the operator must keep the prefixes free of links made by others. The handle check uses `/proc/self/fd` on Linux, `F_GETPATH` on macOS and NetBSD, and `F_KINFO` on FreeBSD; where that facility is unavailable (procfs not mounted, OpenBSD and other systems) a load under path prefixes returns `Unsupported`. Without prefixes no such facility is needed. On Windows the provider refuses UNC, device-namespace and network-drive paths, and a link or junction whose target is one, before opening any of them, then verifies the opened handle's final path. Builds without the provider bind the same signatures and return `Unsupported` to callers with network access. Direct streams and buffer engines share a TLS ID table, separate from ordinary socket IDs. The runner releases remaining TLS resources at the end of execution. The `*_overlapped` services below overlap and can be cancelled; the other TLS services do not overlap. The buffer engine returns promptly and the Neura stream implementation decides how to wait for peer data.

**DTLS services.** These network services drive OpenSSL 4.1's DTLS 1.3 engine over a caller's bound UDP socket. The circuit supplies whole datagrams and sends the returned packets to a fixed peer. The engine checks numeric sender address and port before admitting a datagram. The server validates an address cookie before accepting the connection: a first flight without a valid cookie gets only a HelloRetryRequest, and the server sends its handshake flight and accepts a connection only after the cookie returns. OpenSSL 4.1's listener is not strictly stateless for an unvalidated address, though: it retransmits that HelloRetryRequest and, after a first flight from an address, ignores further first flights from it for a while, including the real peer's if a spoofing sender claimed its address first. The peer's retransmitted first flight is then answered, so this delays the handshake by about one retransmission interval rather than blocking it. The engine admits only its configured peer address, so this state is bounded to one address per engine. The client verifies the chain and the configured DNS name or IP address. An explicit CA on the server requires a verified client certificate. The caller's explicit credentials use the same opened-file authorization as TLS.

**Redirects.** The provider follows 301, 302, 303, 307 and 308 with a single `Location`, at most ten times. A 303 (except for `HEAD`), and a 301 or 302 of a `POST`, continue as a `GET` without the body, `Content-Type` and `Content-Encoding`; the others keep the method and body. A redirect that returns to a URL already requested with the same method is a loop. Three rules protect the caller's request:

- A redirect from `https` to `http` is never followed (23).
- When a redirect changes the origin (scheme, host or port), only the caller's `Accept`, `Accept-Language` and `Content-Language` fields are sent on; every other caller field, authorization, cookies and API keys included, is dropped.
- A redirect that changes the origin and would resend the request body (307, 308, or 301 and 302 of a method other than `POST`) is not followed (24).

A `Location` field on a response that is not a redirect has no effect, repeated or not.

**HTTP client origins.** `--allow-http-client=origin,...` grants the service for the listed origins only, and `--allow-http-client=` for none. An origin is `http` or `https`, a DNS name or an IP literal (IPv6 in brackets), and an optional port; a path, a query or a wildcard is refused when the option is read. Without a list, the grant reaches every origin, loopback, private and link-local addresses (cloud metadata services among them) included, as in 0.3.0; set a list wherever the program does not need that. With a list, the provider checks every request and every redirect, and every address it connects to:

1. The URL's scheme, host and effective port must equal a listed origin's. Names are compared in lower case, without a final dot. Anything else returns 14 (`CapabilityDenied`) before a name lookup, and version 2 names the origin.
2. A listed numeric origin allows exactly its address. An IP literal with a final dot (`http://1.2.3.4.:80`) is that address too, so it matches the numeric origin and connects only to that address, whatever a lookup of the dotted text answers.
3. A listed name allows the global addresses it resolves to. A non-global address (loopback, private, link-local including 169.254.0.0/16 and fe80::/10, unique-local, shared 100.64.0.0/10, unspecified, multicast, documentation and the other special-purpose ranges, and the IPv4-mapped forms of all of these) is allowed only when a numeric origin with the same scheme and port lists it. `localhost` is a name: `http://localhost:8080` needs `http://127.0.0.1:8080` (or `http://[::1]:8080`) as well.
4. The check is made on each candidate address before its connect attempt, for every connection, so a name whose answer changes between connections cannot bypass it. Refused candidates are skipped; when none remain the request returns 14 and names the origin, not the addresses.

The list is part of the grant wherever the grant goes: the native executable's policy (container version 4), the runtime service's launch envelope, `neura-server-host` and its workers, the debugger's `capabilities.http_client` (a Boolean or a list of origins), and a project's server and desktop targets, which pass the `http` and `https` origins of their `origins.connect` list ([Projects](../apps/Projects.md)).

The native provider bounds request and response bodies to 8 MiB, admits at most 16 overlapping exchanges and follows at most ten redirects. Each chunk-size line and the trailer section of a chunked response are bounded to 16 KiB; the number of chunks is not. The chunk framing as a whole (size lines with their extensions, and each chunk's closing CRLF) may total at most 64 KiB or eight times the body bytes received so far, whichever is larger, and a response past that returns 16 (`TooLarge`). A one-byte chunk without extensions needs five framing bytes, so only long chunk extensions reach the bound. It returns representation bytes without decompressing content encodings. A malformed request returns 4 (`InvalidInput`), an unverified TLS identity returns 2 (`PermissionDenied`), an origin outside the grant 14 (`CapabilityDenied`), and missing TLS or an unknown URL scheme returns 13 (`Unsupported`). It returns 16 (`TooLarge`) for size limits and 17 (`Busy`) when the in-flight limit is reached. A closed peer without a complete response, ambiguous or invalid response framing, or a redirect loop returns 18 (`OutcomeUnknown`). A refused redirect returns 23 (from HTTPS to HTTP) or 24 (a body across origins). An HTTP/2 peer that states it did not process the request, by a GOAWAY whose last stream ID is 0 or by `REFUSED_STREAM`, before any response head, returns 25 (`NotProcessed`): the request may be retried. The library reports these codes as `http.TooLarge`, `http.Busy`, `http.OutcomeUnknown`, `http.RedirectDenied` (23 and 24) and `http.NotProcessed`. At process exit the provider cancels and joins its workers before the TLS library is torn down. [Browser HTTP fetch](Providers.md#http-fetch)

The fully static launcher serves cleartext HTTP/1.1 with numeric addresses and `localhost`. TLS, DNS name lookup and HPACK return `Unsupported` on that profile.

The HPACK services are available in builds with `NEURA_ENABLE_SERVER_HTTP2`. Their inputs and outputs are bounded to 64 KiB and 256 fields, and each call starts with an empty dynamic table. HTTP/2 connection setup, raw frame writes and close in `Std.Net.Http.H2` use the overlapped TLS services and the network capability, so a stalled peer parks only the calling task. `Std.Net.Http.Fetch` handles full request exchanges over HTTP/2.

**Application services.** A server image binds `neura.http.server.next`, `respond`, `body.read`, `body.write` and `body.close` (the `http_server` group) and `neura.app.config` and `neura.app.log` (the `app` group). Every runner registers them. Only a request worker of `neura-server-host` grants the two groups and answers them; under `neura run`, `neura test` and a native executable each call fails with 14. The worker operates under the assigned request's deadline. A call out of order (a second `next`, a response before `next` or after its head) fails with 4, and a response body beyond the host's limit with 16. Header and log fields cross as one text list of alternating names and values. The signatures, the worker protocol and the limits are in [the backend design note](../design/Backend030.md#implementation-status-2026-11-17) and [Server host](ServerHost.md). Error codes 16 to 22 (`TooLarge`, `Busy`, `OutcomeUnknown`, `PoolExhausted`, `VersionMismatch`, `ConstraintViolation`, `Serialization`) belong to these providers; the library maps them to `Other` in this release. Codes 23 to 25 (`RedirectDowngrade`, `RedirectBody`, `NotProcessed`) belong to the [HTTP client services](#http-client-services), whose library maps them to `http.RedirectDenied` and `http.NotProcessed`; `host_error` in `src/nvm/providers.hpp` holds the shared table.

**SQL services.** `neura.sql.pool`, `acquire`, `release`, `begin`, `commit`, `rollback`, `execute`, `query`, `open_cursor`, `fetch`, `close_cursor` and `detail` (the `sql` group) serve `Std.Data.Sql`. Every runner registers them; they answer only where an SQL exchange exists: a request worker of `neura-server-host` with pools, which forwards each call to the host, and `neura run` and `neura test` with `--sql-pool`, which answer in process. Elsewhere each call fails with 14. They do not overlap: a statement holds the execution until it ends or its deadline interrupts it. `Std.Data.Sql` maps their codes, 16 to 22 included, to its own `ErrorKind`. Values cross as four parallel lists, and an error's detail text is read with `neura.sql.detail`, which answers in the execution and so is recorded and replayed. See [SQL](Sql.md#host-services).

**Entropy.** `neura.entropy.fill` reads only the operating system's cryptographic generator: `getrandom` on Linux, `getentropy` on macOS and the BSDs, `BCryptGenRandom` on Windows. When the generator fails the request fails with 100; there is no weaker fallback. Two more version 1 services of the entropy group serve `Std.Crypto`:

| Service | Parameters | Success | Behavior |
| --- | --- | --- | --- |
| `neura.entropy.hardware` | int32 count (at most 1 MiB) | uint8 list | Exactly the count of bytes from the processor's seed source: `RDSEED` on x86-64, `RNDR` on AArch64 Linux, each word retried up to 1,024 times. 13 (`Unsupported`) when the processor or platform has no such source, 100 when it keeps failing |
| `neura.process.generation` | | uint64 | A token that changes in a POSIX fork child and for supported guest snapshot restores. Every Linux build checks the PID alongside `pthread_atfork`, reads coherent snapshots at offset zero from a cached `/dev/vmclock0` descriptor using the version-1 ABI independently of build headers, and observes kernel vmgenid uevents on drivers that emit `NEW_VMGENID=1`. Each fork child opens its own event queue. Windows polls `VmGenerationCounter` with `IOCTL_VMGENCOUNTER_READ`; its published control code requires both read and write access. Missing or inaccessible optional drivers, an unknown VMClock version or layout, and unexpected read errors degrade to the remaining detectors. A transient open or read failure such as `EMFILE` or `EIO` is retried on the next call instead of disabling VMClock for the process. Guests need a usable interface to report restores |

Both are recorded and replayed like every request, so a replay sees the same bytes and the same generations.

**Secret memory.** The NVM cannot lock, pin or promise to clear its own heap: host values are copies, a service cannot hold a heap object, and the collector moves and copies storage. So the runtime keeps secrets *outside* the heap instead. Five version 1 services of the entropy group give a program buffers the host owns, addressed by handle (`Std.Crypto.Internal.LockedMemory` binds them for `Std.Crypto`):

| Service | Parameters | Success | Behavior |
| --- | --- | --- | --- |
| `neura.memory.lock.create` | int32 size (1 to 65,536) | int64 handle | Zero-filled private pages. Linux requires `MADV_DONTDUMP`, `MADV_WIPEONFORK` and `mlock`. Windows requires `VirtualLock` plus `WerRegisterExcludedMemoryBlock` before secret bytes are written; the provider adjusts working-set limits while buffers live. 16 (`TooLarge`) past the 1 MiB run budget or host lock quota; 13 (`Unsupported`) without the platform exclusions or in a recording run |
| `neura.memory.lock.write` | int64 handle, int32 offset, uint8 list | void | Copies the bytes in; 4 outside the buffer |
| `neura.memory.lock.read` | int64 handle, int32 offset, int32 count | uint8 list | A copy out, as an ordinary heap value |
| `neura.memory.lock.equal` | int64 handle, uint8 list | bool | Whether the bytes equal the whole buffer, comparing every byte of the buffer whatever the input |
| `neura.memory.lock.release` | int64 handle | void | Zeroes the pages with `explicit_bzero` or `SecureZeroMemory`, unlocks and releases them; the handle is never valid again |

A handle that was never created, or was released, is 4 (`InvalidInput`); handles are numbered from 1 in each run and never reused. The runner releases every buffer, zeroed, when the run ends, by completion, trap or process exit through the runner. What these services guarantee covers the host buffer only: while it exists its pages are locked against swap and zeroed before release. Linux excludes the pages from core dumps and zeroes them in a forked child. Windows excludes the pages from Windows Error Reporting dumps; this does not restrict independent debuggers or other dump writers. They do not cover the bytes a program writes into a buffer or reads out of it: those are ordinary heap values, which the collector may copy and does not clear, as are the host's own transfer copies of them. Nor is a process killed by `SIGKILL` cleared: the system reclaims its pages. A recorded run cannot create a buffer, because the trace would hold every byte written to it; replay answers what the recording answered. Linux and Windows provide their respective contracts above; other platforms answer 13 to `create`. Generic `Secret<T>.lock` protects a serialized copy only. The original `T`, its aliases and prior exposures remain ordinary values and are not erased by locking; callers must erase or retire them separately.

**Native calls.** A `neura.ffi.call` signature is a version byte (1), a little-endian `uint16` fixed-argument count (65535 for a function that is not variadic), a `uint16` argument count, the result type, and each argument type. A type is one tag: 0 void, 1 `_Bool`, 2 through 9 the signed and unsigned 8-, 16-, 32-, and 64-bit integers, 10 `float`, 11 `double`, 12 a pointer, or 13 a struct followed by a `uint16` member count and the member types. Arguments are the values' bytes back to back in native byte order, each exactly its type's size, and the result is the result type's bytes. A variadic argument must not be a `float` or an integer narrower than `int`. A malformed signature or argument list fails with code 4 before the call. The runner frees every arena and unloads every library when a run ends. Native code runs in the runner's process, outside the NVM's checks ([Foreign interop](../lang/ForeignInterop.md)).

A read requests at most 1 MiB, and so does an entropy request. A run holds at most 1,024 open file IDs and 1,024 open socket IDs; an open beyond that fails with code 100. When a run ends, by completion, trap, or process exit, the runner closes every file and socket it left open. `neura test` does the same after each test.

**Capabilities.** The console services and `neura.process.exit` are always available. Except for capability-free codecs, other services belong to a capability group. Only server request workers grant `http_server` and `app`. The `neura` command-line tools grant the ordinary groups by default. Raw sockets require `--allow-raw` and network access. Outgoing HTTP requests require `--allow-http-client`. `--deny-fs`, `--deny-net`, `--deny-raw`, `--deny-http-client`, `--deny-env`, `--deny-clock`, `--deny-entropy`, `--deny-native`, and `--deny-all` turn groups off. `--allow-*` options, including `--allow-fs=prefix,...`, grant them again in command-line order. The C++ type `nvm::Capabilities` that an embedder passes to the providers denies every group until the embedder grants it. A service that is not granted still binds, and each call fails with code 14. With path prefixes, the provider resolves each path to an absolute path the way the operating system would, following symbolic links, and allows it only at or below a resolved prefix; operations on an entry itself (remove, rename, make directory, stat without following links, create) check the resolved parent and the final name. TLS and DoQ authorize the same opened file whose contents they load.

A failed console write traps with reason 3 when it comes from `Console.print_line`; the other console forms return the failure as an `Io` error. For `console.print_line("Hello, World!")`, the image stores the string in its constant pool. A graph selects a host-call exit whose argument names that constant. The bound console handler writes the line and NVM resumes at the exit's success block. The entry function's `ExitCode` becomes the process status. A trap yields a diagnostic, and `nvm::exit_status` gives the process status for its class, the `Std.Program.ExitCode` variant that names it ([Errors](../lang/Errors.md)). The embedding API exposes the full status or structured trap independently of the platform's exit-code range.

The test assertion services `neura.test.assert` and `neura.test.assert_equal_int32` are retired along with the built-in `Test` module. An image built earlier that imports them fails to bind, before it runs; an earlier image whose only import is `neura.console.write_line` still runs.

**Overlapping and cancellable services.** In an image with tasks, a service may declare that it *overlaps* (`HostService::overlapping`): the task that calls it parks, the other tasks run, and the completion is delivered at a later scheduling point ([Concurrency, section 10.4](../lang/Concurrency.md#104-host-io)). The standard overlapping services are `neura.net.connect`, `accept`, `read`, and `write`, `neura.console.read`, and `neura.clock.sleep`. Each exists twice: version 1 keeps its contract and overlaps without being cancellable, and version 2, which has the same signature and behavior, is the cancellable form the library binds. A cancel request reaches a version 2 request when its task's scope is cancelled while the request is pending. The provider then answers exactly once: with the completion, if the operation finished before the cancel request was processed, and otherwise with error 15 (`Cancelled`; the library's `IoErrorKind.Cancelled`). A write that stored some bytes completes with that count, so a cancelled write with nothing stored answers 15 and one that stored a prefix reports the prefix. `neura.net.connect` resolves the name before it returns, so name resolution holds up every task for its duration. Native `neura.http.fetch` overlaps and is cancellable at versions 1 and 2. File services and console writes complete before the scheduler continues. Without tasks, every service is served as before, version 2 included.

A service starts an overlapping request with `begin`. It returns the completion if it finished at once or a `PendingOperation` with a wait source, an `attempt` function that tries to finish without blocking, and an optional deadline on the run's task clock. A deadline has an `expire` completion for an attempt that still cannot finish. The driver (`src/nvm/driver.hpp`) checks readiness without blocking at scheduling points and delivers the answers in ascending sequence order. When no task can run, the native driver waits until a wait source can proceed or the earliest deadline passes. It starts no thread. For virtual time it moves the clock to the earliest deadline instead of blocking on that deadline.

An operation may also give a `wake_at` function, which is unset by default. Given the task clock's reading, it returns the reading at which `attempt` must run again even though the wait source is not ready, or no reading when there is none. A provider recomputes it from its own timers, such as a QUIC connection's loss, acknowledgment and idle timers. Reaching a wake-up attempts the operation but never expires it; only the deadline does. The native driver bounds its wait by the earliest wake-up. Under virtual time a wake-up bounds only the real wait for readiness and never moves the virtual clock. Steps and traces do not depend on it, and an operation without one behaves as before. A guard keeps a wake-up from causing a busy wait: each attempt in a row that only a wake-up caused, and that did not finish, doubles the real time before the operation's next wake-up counts, from 1 ms up to 32 ms. Readiness of its wait source and its deadline still attempt it at once.

A service can also share a provider's *background work* (`HostService::background`): processing that must continue while the provider holds live resources, whether or not a request is pending on them, such as a QUIC connection's acknowledgments, buffered data, retransmissions and idle timer. The driver of an image with tasks adds each distinct background work once, runs it on every check (the check of a single cancellation excepted), and includes its descriptors and its wake-up in every wait. Background work never completes a request, so it does not keep a run that cannot otherwise progress from ending in a deadlock. A replay calls no provider, so it never runs. It runs only at driver checks, which a computing task with nothing outstanding does not reach: live background work does not count as outstanding, because that would turn the task's quantum ends into scheduling decisions and change its ticks and trace (a run whose other task has a request outstanding records the same program's first later request at tick 20 instead of tick 0 after 20,000 loop iterations). An image without tasks runs no background work: its waiting calls do their own processing until they return. At the end of a run the QUIC provider closes every connection still open, after its buffered data, within two seconds.

The default wait source allows an attempt at each check. A POSIX source names a descriptor and read or write interest, or both. A provider whose interest changes can supply the current descriptor and events together on each check. Windows sources are borrowed handles that stay valid for the pending operation and remain signaled when checked, such as manual-reset events. The driver uses `poll(2)` on POSIX and `WaitForMultipleObjects` on Windows. Interests in the same descriptor, from several operations or from an operation and a provider's background work, share one wait entry; each interest is ready when the descriptor reports the events it asked for, or an error or hang-up. On Linux, `NEURA_IO_BACKEND` in the environment selects another backend, read once per process. `epoll` uses `epoll(7)`: one level-triggered epoll set per driver thread, kept between checks, with each check's descriptors added, changed or removed. `io_uring` uses an `io_uring(7)` ring per driver thread, through system calls without liburing: each check submits a one-shot poll per descriptor and a timeout for a bounded wait, waits for the first completion, then removes the polls that did not complete and reaps every completion before it returns. A kernel without the backend, one where it is disabled (`kernel.io_uring_disabled`, a seccomp filter), a check with more descriptors than the 256-entry ring takes, or a descriptor epoll refuses (such as a regular file) falls back to `poll(2)`. The backend changes how readiness is gathered, never the order of completions: ready operations are applied in request sequence order whichever backend reported them, so a recorded trace is the same under both. `poll(2)` stays the default.

An external source uses a separate signal token for each pending operation. The embedding loop keeps the pending queue and calls its nonblocking `poll()` after a provider signals or a deadline passes. Repeated signals coalesce into one attempt. The check consumes the signal before the attempt, even when the attempt leaves the request pending. A signal arriving after consumption remains available for the next check while the request is pending. The blocking native driver checks external tokens at short intervals. Cancellation first checks for an available completion, then asks the provider to settle a cancellation if needed. The provider resolves any race with completion during that call. An answered request ignores later signals.

## Kernel calls

A kernel exit (NVR 1.6, state operation 24) calls one of the built-in C kernels compiled into the runtime ([Kernels](Kernels.md)) through the image's `KERN` record. The loader has already checked that the runtime has the kernel at the record's ABI version and that the signature is the kernel's. The NVM performs the call in this order:

1. **Resolve the arguments.** Each reference argument is checked like an operand of any state operation. Text, and an array or list for a read-only view or byte string whose storage holds each element at the width the parameter reads, are viewed in place. An array or list stored wider than that, after a value that did not fit its declared width, is packed into a buffer that the execution reuses: a byte per `uint8` element, and so on. A writable view and a state are packed too.
2. **Charge the steps.** The kernel's step charge is evaluated on the arguments' lengths and scalar values and added to `steps` before the kernel runs. If it would take `steps` past `--max-steps`, the run stops with the step-limit trap at this exit, as a block step would. With `--profile`, the steps count for the function that made the call and for the running task. The charge depends only on the arguments, so the count, and the point at which a step limit stops a run, are the same in every execution mode and on every host.
3. **Run the kernel.** Each output buffer is sized from its declared capacity formula; scratch space from its declared size. A kernel that still reports `NEURA_NEED_CAPACITY` is called again once with the reported capacity and no second charge. A `NEURA_TRAP_*` status stops the run with the program trap (reason 3) and the status's message, the same trap and text as the Neura code the kernel replaces. A `NEURA_ERR_*` status of a kernel with an outcome result becomes the outcome's status and error offset.
4. **Write back and allocate.** Writable views and states are copied back into their arrays or lists only when the kernel did not trap. A text, bytes, or outcome result is then allocated through the allocator that `ConstructText` and collection allocation use: the same handle order, heap-cell accounting, safepoint, and collection schedule. The outcome tuple's value is allocated first and kept rooted while the tuple is allocated.

A kernel call is not a host request. It issues no request and needs no import or capability, so nothing is written to a `--record` trace, `--replay` needs nothing for it, and `--deny-native` and the other capability flags do not affect it. It runs the same way in a task, in an isolated parallel item, in a fleet member, and in the static launcher. `--stats` does not count kernel calls: its fixed figures are part of the cross-mode agreement above, and the steps already include each call's charge.

**What a kernel must guarantee.** A kernel reads only its arguments and writes only the buffers, state, and result locations it is given; it keeps no state between calls except the state byte array the caller holds; it never allocates, calls back, or reads the clock, the environment, the locale, or a file; and it gives the same results and statuses for the same arguments on every platform, with IEEE 754 binary64 arithmetic without contraction and canonical NaNs. Its step charge and buffer formulas are functions of the argument lengths and scalar values only, its charge covers the most work those arguments allow within a constant factor, so no call does unbounded work for a bounded charge ([Step charges](Kernels.md#running-a-kernel)), and its capacity formulas are always large enough. These are the rules of `src/kernels/neura_kernel.h`; a kernel that breaks one breaks the determinism of every image that calls it.

## Callbacks

An image's `CALB` table names functions that a host service may call while it serves a request ([NVR](NVR.md#imports-and-optional-source-maps)). The runner passes each request a callback context. Calling a callback runs that function on the same heap and globals, above the frame suspended at the host call, until it returns; the host requests it makes are served the same way, so callbacks can nest. Steps, frames, and heap cells count against the run's limits.

A trap, a process exit, or a failed limit during a callback ends the run. The callback returns nothing to the service, the service's eventual response is ignored, and the run reports how it ended. `nvm::Execution::invoke_callback` is the embedding interface.

`Std.DynamicForeign` registers `neura.ffi.upcall` version 1 with parameters `int64 stub, uint8 list arguments` and result `uint8 list`. `neura.ffi.upcall.create(int64 arena, int64 stub, uint8 list signature) → int64 address` returns a native function pointer, a libffi closure, that packs its arguments as `neura.ffi.call` does and calls the callback with them. It writes the packed result back to native code. A stub is valid only while its arena is open and while a `neura.ffi.call` from the same run is in progress; native code that calls it at any other time ends the process with status 134 and a message on standard error. A variadic signature cannot be an upcall.

## Determinism, limits, and observability

Given the same validated image, initial inputs, resource limits, and host completion trace, a run yields the same exit selections, effects, state updates, and terminal outcome. Clock readings, file contents, and similar external responses enter through the host boundary. Tests can supply those responses from a trace and verify the emitted request sequence. `nvm::record` runs an image with bound services and records each request, as the import's name and version with its arguments, together with the response and the terminal outcome. `neura run --record <file>` writes such a trace as text, and `neura run --replay <file>` answers every request from one without invoking any service or needing any capability. The text form starts with `neura-trace 1`, `neura-trace 2` when it records callbacks, or `neura-trace 3` for an image with tasks (see "Traces of images with tasks" below); each `request <import> <version> <arguments>` line is followed by `ok <value>`, `error <value>`, or `exit <status>`, and the file ends with `outcome completed <status>` or `outcome trap <kind> <reason> "<message>"`. Values are unsigned decimal slot bits, quoted byte strings with `\xHH`, `\n`, `\r`, `\t`, `\"`, and `\\` escapes, or bracketed lists; `#` lines are comments. Between a request line and its response, `callback <name> <version> <arguments>` opens a callback the service made, followed by the requests the callback made and `return <value>`, or `ended` when the run ended during it. A replay calls each recorded callback with its recorded arguments before supplying the request's response, and checks that the callback makes the recorded requests and returns the recorded value. A replay reproduces the console output the recorded requests wrote, and a divergence ends with status 1 and a description of the first differing request. `nvm::replay` runs an image, answering each request from a recorded trace instead of real services, and reports whether the image made the same requests in the same order and ended the same way. Requests match by import name and version, not table index, so two images that number their imports differently can be compared. The decompiler tests use this to compare an image with one regenerated from its decompilation. The reference executor runs one block at a time and waits for each selected host call before resuming, except for a service that overlaps in an image with tasks ([Host services](#host-services)). A faster executor must preserve that order where it is observable. Fleets may advance independent runs together while preserving their serial order where it is observable.

NVR 1.5 adds scheduler exits, a poll bit on continue and call exits, and a `TRNS` table of transferable layouts ([NVR](NVR.md#scheduler-operations-15)). The compiler emits them for a program that uses tasks, after checking at source level that what tasks exchange is transferable and what they call is task-safe, and the NVM runs such an image on one deterministic scheduler ([The scheduler](#the-scheduler)). `RunLimits` supplies `max_tasks` (65,536 by default), `max_queued_messages` (1,048,576), `max_pending_requests` (4,096), `task_quantum` (1,024 polls), and `parallel_workers` (1). [Concurrency](../lang/Concurrency.md) specifies the language and [Status](../lang/Status.md) what this release supports.

The loader applies size and count limits before allocating image structures. The runner enforces declared bounds on frame depth, live heap storage, live region cells (NVR 1.7, `--max-stack-cells`), execution steps, and, for an image with tasks, live tasks, values buffered in channels, and overlapping host requests in flight. The task quantum is a scheduling setting rather than a work limit. In a task image, each live frame of every task counts toward the heap-cell limit as one cell plus one per slot, and so do the scheduler's records: 20 cells for a task, 1 for an open scope, 16 for a channel and one more for each buffered message, 8 for a timer, 8 for a guard, and 8 plus the cells of its argument for a parallel-map item. Images without a `TRNS` table keep the previous accounting. Exhaustion traps at the operation that exceeds the configured limit. Limit checks occur before the affected allocation or state mutation. A trap stops further program execution and leaves any completed external effects visible.

Diagnostics identify the runtime fault and, when execution has begun, the function and block. Optional source maps add source locations. A trace can expose block entries, graph exits, and requests and responses. Inspection and decompilation use the executable graph and continuation tables, with source maps as supplemental information.

### The scheduler

An image with a `TRNS` table has tasks. One scheduler runs one task at a time. Its state (task records, the runnable queue, channel buffers and waiter queues, cancellation signals, timers, guards, and pending host requests) is NVM state reached through scheduler exits, as the heap is reached through state operations. [Concurrency, section 10](../lang/Concurrency.md#10-runtime) is the contract for programs; this section states what the runtime does.

- **Queues and identity.** The runnable queue and every waiter queue are FIFO. The root task is task 0, and tasks, channels, and timers are numbered in creation order.
- **Decisions and ticks.** A scheduling decision takes a task from the runnable queue and runs it until its turn ends. The tick is the number of decisions made so far (`Execution::tick()`).
- **When a turn ends.** A turn ends when the task parks, when it finishes, or at a poll that finds the quantum spent. A poll is a bit on a continue or call exit, and each one the running task executes adds one to its count for the turn. When the count reaches the quantum, the task goes to the back of the runnable queue if another task is runnable, or if a deadline, a timer, or a host request is outstanding. With nothing else runnable and nothing outstanding, the count restarts and the task keeps running. The second condition gives the driver a scheduling point at which to read the clock and deliver completions while one task computes, so a scope's deadline stops a task that never parks. An image that arms no timer or deadline and issues no overlapping request is scheduled as if that condition did not exist.
- **What the driver sees.** `Execution::advance()` returns to its caller at every host request. Before a decision, while a timer, a deadline, or an overlapping request is outstanding, it returns a `Poll` event; when no task can run but a timer or a request can still wake one, a `Waiting` event; and when a task waiting for a cancellable request was cancelled, a `Cancel` event. The driver answers with `deliver()` for a completed request and with `advance_clock(now)` for a clock reading, which expires the timers and deadlines at or before it. When no task can run, nothing is outstanding, and at least one task is parked, the run ends with the `deadlock` trap.
- **The clock.** Timers and deadlines are readings of a `TaskClock` that the driver supplies: `now()` and `wait_until(deadline)`. The default is the host's steady clock, which is the clock of `neura.clock.monotonic`. `VirtualTaskClock` is the clock of `--virtual-time`: it starts at zero, `wait_until` moves it to the deadline without waiting, and the driver never blocks on it. `StandardServices::set_clock` gives the same clock to the clock services: `neura.clock.monotonic` returns its reading, `neura.clock.wall` its reading after 2000-01-01T00:00:00Z, and a `neura.clock.sleep` that does not overlap moves it by the sleep's length. The clock capability is checked first in each case. When every task is parked, descriptors are pending, and a deadline is armed, the driver moves a virtual clock to the deadline and then checks the descriptors once, so under virtual time a deadline is not held back by I/O that is not ready.
- **Choosing a task.** The reference scheduler takes the first runnable task. `RunLimits::chooser` replaces that choice: a `ScheduleChooser` is called at each decision with the tick and the number of runnable tasks and returns the position in the runnable queue of the task to run. Zero is the reference scheduler's choice, and a position beyond the queue is taken as zero. Every choice is a legal schedule, because only the order among runnable tasks varies. `ExploringChooser` picks uniformly from a seed with a fixed generator (SplitMix64), so a seed names the same schedule on every machine, and keeps each choice that was not the first; `RecordedChooser` replays such a list and reports a position that did not exist. `neura test --schedules` and `--schedule` use them, and `write_schedule` and `read_schedule` in `src/nvm/schedule.hpp` write and read the saved file ([Concurrency, section 14.4](../lang/Concurrency.md#144-testing-concurrent-code)). A chooser decides only among runnable tasks; it does not decide when a host completion is delivered. `RunLimits::schedule` receives the task chosen at each tick, for tests and tools that compare schedules.
- **Observation.** `Execution::dump_tasks()` returns a snapshot of every task, `RunLimits::observer` receives scheduler events, and `RunLimits::profile` adds totals for each spawn site. None of them changes the run.

### Traces of images with tasks

An image with a `TRNS` table records and replays with trace file version 3, which only such an image writes; a trace of any other image stays version 1 or 2, byte for byte as before. The file adds a `settings` line, the issuing task and tick to every request, and the driver's own actions:

```text
neura-trace 3
settings quantum <n> max-tasks <n> max-queued-messages <n> max-pending-requests <n>
request <import> <version> <arguments> task <id> tick <n> [overlapping | cancellable]
ok <value> | error <value> | exit <status> | abandoned
...
deliver <tick> <request> [cancelled]
clock <tick> <nanoseconds>
outcome completed <status> | outcome trap <kind> <reason> "<message>"
```

- `settings` holds the quantum and the scheduler limits of the recorded run. **A replay uses them in place of its own**: `neura run --replay` with another `--task-quantum` or `--max-tasks` still reproduces the run.
- `task` is the task that issued the request and `tick` the number of scheduling decisions made when it did. A request without a mode completed before the scheduler continued. `overlapping` and `cancellable` mark a request that parked its task, by the mode of the service that served it. Its completion line follows the request line, as for every request, though it was delivered later. `abandoned` replaces the completion of an overlapping request the run ended without delivering.
- The `deliver` and `clock` lines follow the last request, in the order they happened. `deliver` names a request by its position among the request lines, from zero, and the tick of the scheduling point where the driver gave the task its completion. `cancelled` says that a cancel request had reached the operation before its answer was delivered, whichever answer it was; the answer is the completion if the operation had finished, and error 15 otherwise. `clock` is a reading of the run's monotonic clock, in nanoseconds, that expired at least one timer or scope deadline; other readings are not recorded. Readings can be negative only in a hand-written trace.
- The outcome gains the trap kinds of the scheduler, among them `deadlock`, `task-limit`, `request-limit`, and `message-limit`. A deadlock is its own outcome and has no message.

A replay invokes no service and needs no capability. At a request it checks the import, the version, the arguments, the issuing task, the tick, and whether the request overlaps; a synchronous request is answered from the trace and an overlapping one parks its task. At a scheduling point (a `Poll` or `Waiting` event of the scheduler) at tick *T* it applies, in recorded order, the deliveries and clock readings recorded at *T*, up to and including the first clock reading, because a reading can cancel a scope and the cancel request is processed before the next scheduling point of that tick. The replay stops with status 1 and names the first difference when:

- a request differs from the recorded one (import, arguments, task, tick, or mode);
- a delivery names a request that is not pending, or a recorded event is left behind at a tick the run has passed;
- the run waits at a tick at which the trace records no delivery and no clock reading, or a recorded clock reading expires nothing;
- the run cancelled a request that the trace does not mark `cancelled`, or the trace marks a request `cancelled` that the run never cancelled;
- the run makes fewer requests than recorded, or the outcome differs.

A replay that finishes without a difference has reproduced every scheduling decision, since each of them follows from the image, the settings, and the deliveries. It cannot tell a delivery moved to an earlier scheduling point where the run behaves the same apart from the tick; the recorded request ticks bound that. A trace without the `settings` line (version 1 or 2) replays an image with tasks whose requests all completed before the scheduler continued, under the caller's own quantum and limits. A run under `--virtual-time` writes the same file with its virtual clock readings and replays like any other, without the option. A trace holds no schedule choices: a recorded run is a run of the reference scheduler, and a schedule explored by `neura test` is saved in a file of its own.
