# GPU execution: design decisions

This page records why the design of GPU execution is as it is, for contributors who change it. [GPU execution](../lang/GpuExecution.md) is authoritative for behavior; where this page and that one differ, that one is right. The identifiers D1 to D18 are used only here.

| ID | Decision | Rationale |
| --- | --- | --- |
| D1 | There are three modes. `auto`, the default, lets the runtime decide by predicted speed. `always` sends every eligible graph to a GPU. `off` uses the reference evaluator only. `--no-gpu` selects `off`. | A GPU loses to the CPU on a single execution (a single request is 22 to 309 times slower), so a forced device would slow most programs. `auto` must therefore be the default and cost nothing when it declines. `always` exists to test and to measure the device, and `off` to get the reference evaluator's behavior and timing. |
| D2 | A device performs graph evaluation only. Frames, slots, exits, state operations, the heap, collection, limits, host requests, and trap construction stay in `Execution::State`. | The graph is the one part of a step that is a pure function of its input lanes. Keeping everything else in one place keeps traps, limits, and traces identical in every mode, and the device is then replaceable without a second implementation of the machine. |
| D3 | No NVR, NIR, or graph profile change. Profile 1 keeps its definition: checked signed 64-bit arithmetic, ascending-source edge order, stored node order. | The artifact must run on a runtime with no GPU and must mean the same everywhere. A device is an implementation choice that has to agree with the reference rule, so it cannot redefine the rule. |
| D4 | The device API is Vulkan 1.0 compute with no extensions and no layers. The Vulkan loader is opened at run time; the build needs only Vulkan headers and `glslangValidator`. | Vulkan 1.0 compute is the lowest common requirement of the discrete, integrated, and software implementations the design was measured on. Opening the loader at run time lets one binary run on machines without Vulkan and keeps the library out of the NVM. |
| D5 | GPU arithmetic is 32-bit two's-complement integer. Exactness comes from the weight budget and the wire bound of section 6, with `wire_bound = 32767`. | Exact integer arithmetic makes results independent of the device and of evaluation order, which floating point would not. 32 bits are the portable integer width on Vulkan 1.0. The measured graphs peak at a neuron value of 29 against a bound of 32,767, and their weight budgets are under 2²⁴, so the bound costs no observed graph its eligibility. A static interval analysis was tried and failed for the largest graphs, so a static weight budget plus a run-time bound is used instead. |
| D6 | The kernel is the layered kernel of section 8: one work group per request, 64 invocations per work group, one barrier per layer. Its source in section 8 is normative. | Compiled graphs are deep and narrow, so one request offers little parallelism within a layer; the parallelism is across requests. One work group per request with a barrier per layer is the simplest form that works on three independent implementations. The kernel source is normative so that the self-test and the exactness argument refer to the same code. |
| D7 | Placement is fixed by the mode. In `always`, every job for an eligible graph goes to the device. In `auto`, placement is exactly the procedure of section 11. In `off`, nothing does. A graph with no neurons is never sent. No other threshold, sampling rule, or cache is added. | A procedure with no hidden knobs can be tested with fixed models and hand-computed expectations. Extra thresholds would make placement depend on tuning that the specification does not state. |
| D8 | When no usable device exists, `auto` and `always` use the reference evaluator and print nothing. `--require-gpu` turns that case into an error before entry. | A program must run the same on a machine without a GPU. A user who needs the device, for example to measure it, has an explicit way to learn that none is available. |
| D9 | The NVM library's default stays the reference evaluator. `nvm::Execution`, `nvm::run`, `nvm::record`, `nvm::replay`, and `nvm::Fleet` use a device only when the caller passes one. Only the CLI applies D1. | Embedders and tests get the reference behavior unless they ask for a device, and the mode policy lives in one place. |
| D10 | Device choice is deterministic: discrete, then integrated, then virtual, then other, each in loader enumeration order. Software implementations (`VK_PHYSICAL_DEVICE_TYPE_CPU`) are used only with `--gpu-software`. | The same machine picks the same device on every run. A software implementation is slower than the CPU for every graph measured, so it is never chosen unless asked for, which lets the tests cover the Vulkan path on machines without a GPU. |
| D11 | The existing CTest entries run with `NEURA_GPU=off`, so their evidence continues to come from the reference evaluator, one execution at a time, and their duration does not depend on the machine. New entries cover fleets, placement, and the GPU path. | Existing evidence keeps its meaning, and a machine's GPU cannot change the duration or outcome of the older suites. |
| D12 | macOS is outside this specification. The CMake option `NEURA_GPU=AUTO` resolves to `OFF` on Apple platforms. The Windows path is specified and unverified, as MSVC builds are. | The Vulkan backend has not been built or verified on Apple platforms, and the Windows loader path has not been verified, so the specification claims neither. |
| D13 | A fleet delivers host requests and results in member order: a member's host request is issued only after every lower-numbered member has finished. A fleet is therefore equivalent to running its members one after another. | Host services keep state per run and tests print in order. Serving requests only for the lowest unfinished member makes the fleet indistinguishable from a serial run, so batching never changes output. |
| D14 | `neura test` and `neura run --each` run their members as a fleet in `auto` and `always`, and one at a time in `off`. A `neura run` without `--each` executes one program and never forms a fleet. | A dispatch costs about the same for one request as for several hundred, so a GPU can pay only when many requests are in flight. A single execution never has more than one. |
| D15 | In `auto`, the decision to open a device is a deterministic function of the image and of the jobs the run produces. Decisions made after that use measured time, so they can differ between runs and machines. No decision can change a result. | Opening costs 40 to 130 ms. Making that decision from the image and the jobs, with generous model constants, makes it reproducible and testable on every machine. Measured time is used only where the model needs to follow a real device. |
| D16 | `auto` prefers the CPU when in doubt: the device must be predicted to take at most 0.75 of the CPU's time. A rejection lasts for the rest of the process. Nothing is cached on disk and no thread is created. | A wrong choice for the GPU costs more than a wrong choice for the CPU, because of setup and variable device timing. A permanent rejection, no stored calibration, and no background thread keep the behavior simple and the run self-contained. |
| D17 | `neura run --each <file>` is the command-line way to give one image many inputs. It is defined in every mode and build, including builds without the GPU. | Many inputs to one image is the workload a device can help. Defining the option in every build keeps scripts portable, and makes the member semantics testable without a GPU. |
| D18 | In `auto`, an Active device is retired when 256 consecutive Active calls kept more than nine jobs on the CPU for each job they placed. Retirement is a rejection with the reason `the device stopped gaining` and is not a failure. The call that retires it depends on measured time, so on the machine, unlike the opening decision of D15. | Without retirement, a device that was opened and kept but declined about 97 percent of the jobs still cost every round the formation of a wide round and the placement bookkeeping, and the 65,536-list Collatz run was slower than the CPU run. Retiring it removes that cost. |
