# Neura Virtual Machine

[Wiki home](https://github.com/Kayyo321/neura/wiki) · [Language overview](https://github.com/Kayyo321/neura/wiki/Overview) · [Feature status and open decisions](https://github.com/Kayyo321/neura/wiki/Status)

The Neura Virtual Machine (NVM) loads and executes a Neura Virtual Runtime image (`.nvr`). An image contains compiled neuron graphs, typed execution metadata, constants, and the host imports needed by the program. This specification defines the NVM execution contract. [NVR format](NVR) defines its binary encoding. [Neuron conversion and execution](Backend) describes the implementation: its run limits, trap reporting, and embedding API, and the decisions the compiler takes where the language is open.

## Toolchain and distribution

```text
hello.nra -> hello.nir -> hello.nvr -> NVM
              typed IR     executable
```

The compiler can materialize versioned NeuraIR as a `.nir` file before optimization. A build from source can pass the same representation internally. Both routes validate NeuraIR, apply the selected IR optimization pipeline, convert the result to neuron graphs and execution metadata, and encode the NVR image. A `.nir` reader must preserve types, symbol identity, region structure, evaluation order, and effects. The human-readable IR listing is a separate interface.

The compiler distribution provides these commands:

```sh
neura emit-ir hello.nra -o hello.nir
neura build hello.nir -o hello.nvr
neura build hello.nra -o hello.nvr
neura run hello.nvr -- arg1 arg2
```

`neura run` loads the image, binds the selected host services, and passes arguments after `--` to the entry function. The loader and executor form a reusable NVM library. A runtime-only distribution uses the same loader and execution contract. A compiled image can move between supported hosts with compatible format and service versions. A [native executable](Standalone) is a runtime-only distribution with a CPU launcher. Its container carries the unchanged NVR bytes and the runner policy: the capabilities, the run limits, and the task settings (the task, queued-message, and pending-request limits, the quantum, and the parallel worker count). The same loader and execution contract apply after extraction. `NEURA_RUN_OPTIONS` can lower the limits and the worker count and cannot change the quantum, which decides how tasks interleave.

## Graphs and continuations

A function has a signature, a frame layout, and an entry block. Each block evaluates a feedforward neuron graph, then takes one declared exit. Blocks can share graph definitions. A loop repeats blocks through continuations. A call uses the callee's entry block and its own frame. The graph produces an exit selector and payload bits. NVM interprets the selected exit descriptor and transports its typed values.

The reference graph profile uses signed 64-bit integer weights and biases, with identity and ReLU activations. For a node, NVM starts with its bias and visits incoming edges in ascending source index order. Each multiplication and running sum uses checked signed 64-bit arithmetic. Overflow traps before the activation. Identity returns the sum. ReLU returns zero for a negative sum and the sum otherwise. Node evaluation order follows the stored topological order. A backend must produce circuits whose intermediate arithmetic is valid for the input domain it claims to support.

An implementation may compute graph output lanes by another method when they equal the reference values and reference evaluation does not overflow. If the method cannot establish both conditions, the reference evaluator supplies the result or reports the overflow.

At the graph boundary, each value occupies a sequence of bit lanes. Lane zero is the least significant bit. Booleans occupy one lane, and integers occupy their declared width with two's-complement encoding for signed values. References cross the graph boundary as 64-bit opaque handles. Every output lane consumed by the selected exit, including the selector, must be exactly zero or one. A selector outside the block's exit table traps. Source arithmetic and comparisons are expressed by the graph, including checks and exits for specified arithmetic failures. Checked neuron arithmetic is an execution rule for the target and is distinct from the source language's arithmetic rules.

A typed value descriptor can read a frame slot, a constant, or an output lane slice. The runtime transports opaque handles and checks their type and validity when used. Language-level equality, arithmetic, and control decisions are represented in the circuit. Execution metadata can transport a constant or a live reference without routing it through a neuron.

### Graph devices

A graph device belongs to one validated image. Each job sends a graph index and its binary input lanes. The device either returns the exact output lanes in the graph's output order or declines the job. A device failure also declines the job. The executor evaluates declined jobs by reference, including the reference evaluator's first-overflow diagnostic. The executor checks selectors and consumed output lanes and owns every continuation, slot, heap object, resource limit, and host interaction. Device evaluation has no host import or trace entry.

For the same image, arguments, limits, and host completions, an execution must agree in every mode, with any device, and whether it runs alone or as a member of a fleet, on:

- every exit selection, slot assignment, state operation, and host request, in order, with the same arguments;
- the terminal outcome: status, or the trap's kind, reason, detail text, function, block, and caller list;
- `steps`, `peak_heap_cells`, `function_steps`, and the host request count;
- standard output and the trap diagnostic on standard error;
- a trace written by `--record`, byte for byte, and the result of `--replay`.

The following can differ:

- Wall time and process start-up time.
- Which evaluator computed a given graph, and therefore the `gpu:` line that `--stats` adds.
- Runner errors that exist only for the GPU options.
- Peak memory of the process: a fleet holds several members' heaps at once.

A device can expose its graph shapes in image order and a failure reason to a placement wrapper. The wrapper can then omit graphs excluded by the device's table limit or demoted after an escape. An empty shape view leaves the wrapper with the image's static shapes. A failure reason retires the device from automatic placement for the remainder of the run.

Embedders can split a block transition using `Execution::begin_step`, then `finish_step` with exact output lanes or `fail_step` with the reference overflow's node index. Begin charges the block's step and resolves its inputs before evaluation. The input view remains valid until the step is settled. Beginning another step or calling `advance` before settling it is an API error. Finishing with the wrong number of lanes rejects the call and leaves the step open. With no device in `RunLimits`, `advance` evaluates by reference.

### Execution tiers

A tier is a method of computing a block's graph outputs. Every tier is held to the equivalence rule above: it may supply a block's output lanes only when they equal the reference values and reference evaluation of the graph does not overflow. The invariants listed under [Graph devices](#graph-devices) hold whichever tier evaluates a block.

**Tier 0, reference.** The evaluator of [Graphs and continuations](#graphs-and-continuations): every node in stored order with checked arithmetic. It is the oracle for every other tier, and it supplies the result, or reports the first overflow, whenever another tier does not.

**Tier 1, lifted blocks.** The library in `src/lift` (`neura_lift`) turns a block into a short program of native 64-bit operations over its whole input values. It accepts a block only when it establishes both conditions of the equivalence rule for every input of the block:

- **Structural proof.** A lifted form states the block's values, its exit condition, and its checks as typed operations ([Numbers](Numbers)) over the block's inputs. Regenerating the block from the form with the compiler's circuit library (`neura_circuit`) must yield a block and a graph identical to the image's. The equality is exact, so the graph computes exactly what the circuit library builds for those operations. Nothing weaker is accepted: no sampling, no exhaustive evaluation, and no source of the form, including a hint stored with the image, is trusted. The form comes from the image's `LIFT` section ([NVR](NVR#lift-hints)), where the converter records the operations it built each block from, or from the decompiler's structural search ([Decompiler](Decompiler#lifting)), which samples the graph by reference only to choose candidates. A converter-recorded form is *shared*: a node it uses twice is one computation, as the converter computed it once, and it lists every operation in the order the block performs it, including one whose only effect is a check, so regeneration builds the block's neurons and checks in the same order.
- **Overflow proof.** Interval analysis gives every wire a range that holds for every 0/1 input. Starting from the bias, each product and each partial sum, in the reference order, must stay within signed 64-bit arithmetic. Each graph output lane must also be exactly 0 or 1. Intervals lose the correlation between the terms of a sum, such as a sum lane and its carry, so two exact refinements narrow a wire's range before its readers use it. Wires whose weighted sum is known to stay in a small range form a group: a threshold pair `relu(L + b) - relu(L + b - 1)` is 0 or 1 for any integer `L`, and so are two halves of a selection once case analysis shows it. A bounded case analysis also evaluates a wire for every assignment of a small cut of wires below it, with each group as one variable. Where the cut's assignments are too many to enumerate together, because a carry chain or a run of selections links every wire of the cut, an exact elimination computes the same range by dynamic programming along the cut's cone in stored order: a state holds the values of the wires a later node still reads and the range of the part of the sum already known, a wire is summed out after its last reader, and states that then agree merge, keeping both ranges. Its cost grows with the number of wires held at once, not with the cut: a ripple carry holds one carry. It narrows the sums and selections of the float circuits node by node, after which their output lanes follow. An output lane whose range is not within [0, 1] is accepted only for one more reason: it sums equality tests that pairwise require opposite values of some lane, so at most one of them holds. Every argument covers all inputs; none samples.

The overflow analysis first runs without its two refinements. Its intervals are then wider but still sound, so a proof it finds is as valid as a refined one, and for most graphs it is found in a fraction of a millisecond. Only a graph it cannot settle gets the refined analysis, whose case analysis can be bounded by a count of work. Running out of work decides nothing: the analysis stops, and it may be run again with more. A bound changes only whether a proof is found, never which. Both proofs of a graph hold for every block that uses it, so a runtime proves each graph once.

The refined analysis is told where to look first. While the structural proof regenerates a block, the circuit library records which gadget instance built each neuron and which wires that instance was given. For each neuron the analysis first tries the cut through those wires, which is the cut the gadget's own argument uses: a multiplier column is bounded through its carry and its partial products rather than through the input lanes far below them. This record is advice and not evidence. A range is established only by evaluating a neuron over every assignment of a cut, which is sound for whatever cut is tried, so wrong advice can cost time or a proof but cannot make one. The analysis runs up to three times: with the advised ranges left to stand, then with its search after each advised cut, then without advice, and only the last run rejects a graph. The case analysis keeps each enumeration under a description of the whole computation with its wires renamed, so the identical cells of a multiplier or the steps of a long division are evaluated once.

The lowering then gives each operation an exact native form. Integer operations use the stated width and signedness, with the failure conditions of the circuit's checks. When an operation fails, the block takes the trap exit of the first failing check, as the selector would, or declines the step when the block has no trap exit for that check. Float operations are lowered only where hardware arithmetic matches the circuits bit for bit. Each binary32 and binary64 operation runs on the hardware, and every NaN result is replaced by the canonical quiet NaN. Comparisons, negation, truncation to integers, and widening conversions of any format are exact. Narrowing to binary32 is rounded by the hardware. Three operations are not lowered: binary16 and bfloat16 arithmetic, and conversions to a 16-bit format, whose rounding the hardware does not provide. A block that contains any of them stays on tier 0. Every other float operation of binary32 and binary64, addition, subtraction, multiplication, and division included, passes both proofs; the proof of a binary64 multiplication or division costs a few tens of milliseconds, the most of any operation, so a block that contains one is lifted only after it has run long enough to repay it (below). A float block runs on tier 1 only with the default floating-point environment, which rounds to nearest even and neither flushes subnormals to zero nor treats them as zero. On platforms other than x86-64 and AArch64, or where `FLT_EVAL_METHOD` is not 0, no float operation is lowered. When a lowered block meets another environment, it declines the step.

Forms come from two sources. The converter records one for every block it can describe (multi-statement blocks included) in the optional `LIFT` section, and keeps only those whose structural proof holds against the block it emitted. Without a hint, the decompiler's search, extended with integer bitwise operations and shifts, which it tries only after the decompiler's own vocabulary fails, recovers one or two operations over at most three input values. A lowered block depends on the graph, the block's input types, its selector, and each exit's kind, trap reason, and output lanes. It does not depend on slot numbers, constants, targets, or the function, so blocks that share a graph and those share one result. A block whose form is not found, or for which either proof or the lowering fails, stays on tier 0. A block whose graph has no neuron needs no proof: nothing can overflow, and each output lane is an input lane, which holds a bit. Tier 1 reads such a block's lanes straight from its input values.

#### Tier 1 in the executor

`neura run`, `neura test`, `run --each`, fleets without a graph device, the parallel items of a run, and task images all use tiers 1 and 2 by default. A step of a block on tier 1 is a reference step with another way of computing the graph's outputs:

1. The step is charged and the scheduling decision made exactly as by reference, and the block's slot inputs are checked for initialization in input order. An uninitialized slot traps with the same detail, at the same step.
2. The input values are read whole from their slots and constants, without expanding them into lanes, and the lowered block computes the selected exit and every value an exit reads. When a check fails, it selects the trap exit of the first failing check, as the selector would.
3. The exit is committed by the reference commit: values are resolved against the pre-transition frame in the same order, references read from lanes are checked against their types as before, and the assignments, state operation, call, return, or host request follow unchanged.

When the lowered block declines a step (a float environment other than the default, or a failed check whose trap exit the block lacks), that step is evaluated by reference. So is every step of a block without a lowered form. Nothing else changes: one block is one step, `steps`, `function_steps`, `peak_heap_cells`, every trap's kind, reason, detail text, location, and caller list, the host requests, standard output, and a `--record` trace are those of tier 0, and so is a `--replay`.

The lifted blocks of an image live in one `nvm::TierCache` that every run of the image can share (`RunLimits::tier_cache`): `neura run` and `neura test` create one per image, a fleet without one shares its own among its members, a run without one keeps its own, and parallel items use their run's. A lowered block, once published, is immutable. A block with a hint is proven after it has run 4 times, so a block that runs only once or a few times, as start-up code does, is never proven; a block without one is searched for after 2,000 runs, both counted over every run that shares the cache. The refined overflow analysis may use at least about 16 ms of work, enough for a binary64 multiplication or division at the first attempt, and beyond that work in proportion to the steps the block has run times its graph's edges, about twice what the block has cost on tier 0; a search may use wall time in the same proportion, an eighth of that cost. These figures were chosen by measuring the CPU time of the wall-clock benchmarks ([Benchmarks](Benchmarks)) and of `neura test` over standard-library areas, where they lift float blocks soon enough that proving, not tier 0, is most of a short float program's time, without slowing start-up. An attempt that runs out keeps what it settled, and the next attempt resumes there rather than starting over; it is made once the block's allowance has grown enough for the rest, judged by the share of the graph the attempt reached (at least eight times as many runs). The searches of one image stop after 250 ms in all. A proof or search that fails is remembered and never repeated. All of this decides only which blocks run lifted, and when.

#### Tier 2, regions

Tier 2 runs proven blocks one after another without returning to the step dispatcher between them. Its unit is a **region**: blocks of one function, entered at one block, compiled together into one program (`src/nvm/tier2.hpp`).

**Formation.** A region starts at a block that tier 1 runs lifted, wired, or empty, and takes in the blocks reachable from it through continue exits and through the state operations that run inside a region (below), as long as tier 1 runs each of those lifted, wired, or empty too, up to 128 blocks. Each block keeps its exits: one that leaves the region is taken by tier 1. The dispatcher counts its arrivals at a block, over every run that shares the cache, and forms the block's region at the thousandth (at the first under `NEURA_TIER_EAGER=1`). While blocks the region would reach are still being proven, formation waits, up to eight times as long, and a region formed without them is formed again later, at most four times. No region starts at a block with no exit that can stay in one. A formed region is immutable and shared by every run of the image, like a lowered block.

**What a region runs.** Inside a region a block's exit is one of:

- a continue exit to a block of the region, followed directly, with its poll when it has one;
- a continue exit to a block outside the region, after which the region **leaves**;
- a state operation that only reads or writes storage that already exists: `ReadTag`, `ReadField`, `WriteField`, `ReadGlobal`, `WriteGlobal`, `ReadLength`, `ReadElement`, `WriteElement`, `ReadVersion`, `TextEqual`, `ClassIs`, `ClassCast`, and `ScalarText` when it selects one of an enum's names. The region calls the executor's own state-operation code with the same arguments, so its checks, traps, and trap texts are the same;
- any other exit (a call, return, host request, scheduler operation, trap, message trap, or a state operation that allocates, grows, frees, builds text, or calls a kernel). The region does not take it: it **deoptimizes** at the block, and tier 1 runs the block.

**Steps and polls.** Each block a region completes is one step. Steps are added in bulk when the region ends: to the run's count, under `--profile` to the region's function (a region never leaves its function, so the attribution is exact) and to the running task. Nothing inside a region reads the count. The region's entry, and every block a loop in it returns to, is a checkpoint: there the region checks that the most blocks any path can take before the next checkpoint or the region's end fits in what remains of `--max-steps`; that under a scheduler the most polls such a path takes keep the task's count below its quantum; and, in a fleet, that the blocks fit in the rounds the fleet allows. If one does not fit, the region deoptimizes at that block and tier 1 runs on, one block at a time, so the step-limit trap, the end of a turn, and every fleet round happen at the block and with the counts of tier 0. A fleet counts a region's blocks as rounds.

**Deoptimization.** A block commits its exit (its assignments, a state operation's result, its poll, and its step) only after everything that can fail in it: a check of a lifted operation, a reference read from lanes, a state operation, a selector. When one fails, or the exit is one the region does not take, the region writes back every slot it caches, with the frame as it was when the block was entered, and sets the frame's block to it. Tier 1, and tier 0 when tier 1 declines, then runs that block from that state, producing the trap's kind, reason, detail text, function, block, and caller list, or the call, return, request, or allocation, with the reference code.

**Slots and the collector.** A region caches the slots it reads and writes in registers and writes them back, with their initialized flags, whenever it leaves or deoptimizes. Nothing in a region allocates, so no collection can run while a reference lives only in a register, and at every safepoint the frame holds what it holds at tier 0. A slot that some path reads before writing must be initialized when the region is entered, or the region is not entered; every other read follows a write on every path, and a slot never becomes uninitialized in its frame, so no read inside a region can find one uninitialized.

**The region program** caches slots in registers, loads constants at entry, runs each lifted block's operations with the code of tier 1, branches directly between blocks, and has explicit write-backs, deoptimization points (each naming the block it re-runs; the slot registers are the map), checkpoints, and loop heads, so a native compiler can take it as its input. A few local rewrites, each justified inside the region, make it shorter: a mask is dropped where an analysis of the bits each register can hold shows it changes nothing (slot registers are checked against their types' widths at entry, or the region is not entered); a checked addition or subtraction of 1 becomes unchecked when a comparison on every path to it shows the counter is below its type's largest value (or above its smallest), the check staying in the image; operations whose results nothing reads are removed; and a result is written into its slot register directly when nothing between the operation and the commit can deoptimize or reads the slot. A region runs as native code where that is enabled (below), and otherwise in a portable interpreter.

#### Native compilation

The native code generator (`src/jit`) compiles a region program to machine code, which runs in place of the region interpreter. It is part of tier 2: below `--tier=2` nothing is compiled. A region is compiled once, synchronously, by the first run that enters it with native code enabled; every run that shares the tier cache shares the code. Nothing depends on timing: there is no background thread, and whether a region runs compiled changes only its speed.

**What is compiled inline.** Moves, masks, gathers, stores with their initialized flags, branches, switches (an invalid selector deoptimizes), jumps, the step count of completed blocks, budget checks, leaves, and deoptimizations; and the lowered integer operations of 1 to 64 bits: addition, subtraction, negation, and multiplication with their overflow checks, division and remainder (a zero divisor fails), comparisons, boolean and bitwise operations, shifts (a count of at least the width fails), index checks, and integer conversions. Each is compiled from the expression `lift::evaluate` uses (`src/lift/evaluate.hpp`), for every 64-bit operand value: the same masks, the same sign extension, the same failure conditions. Where a condition is exactly the processor's carry or signed-overflow flag (a 64-bit addition, subtraction, or multiplication), the check branches on that flag to a deoptimization stub. The float operations of binary32 and binary64 are compiled inline too: addition, subtraction, multiplication, division, negation, comparisons, conversion between the two formats, and conversions to and from integers of 1 to 64 bits. Each follows `lift::evaluate_float` (`src/lift/lowered_block.cpp`) with the processor's own scalar instruction (SSE2 on x86-64, scalar floating point on AArch64; never a fused multiply-add, AVX, or x87): it reads a binary32 operand from the low 32 bits of its register and zero-extends a binary32 result, replaces every NaN result with the canonical quiet NaN, negates by flipping the sign bit (a NaN keeps its payload), compares unordered operands as the reference does, converts an unsigned integer of 2^63 or more by the reference's halving with a sticky bit, and checks a truncation against the integer range of its width. A truncation that is NaN or outside the signed 64-bit range calls the helper. The code relies on the default floating-point environment, which the entry rule guarantees, and never changes it. An operation writes its register only after its checks pass, so a deoptimization finds every slot register as the block was entered.

**What calls helpers.** Signed division and remainder by -1, float operations of the 16-bit formats, a float truncation outside the signed 64-bit range, and instructions of other widths call `lift::evaluate` itself, the interpreter's code, so they are bit-exact with it by construction. A region that computes floats is not entered at all in a floating-point environment other than the default (the entry rule above). A reference check, an inline state operation, and a poll call the executor's own code, with the same arguments, checks, traps, and trap texts. Helpers are reached through a table in the context the code receives; the code contains no address of the executable, so it works in the static launcher too. A helper that catches an exception other than a trap returns to the code, which returns at once; the executor then rethrows it where the interpreter's would have left the region.

**Registers.** Region registers live in the executor's register array. The registers the program uses most are kept in machine registers for the whole program (7 on x86-64, 13 on AArch64): they are loaded at entry, and stored before every helper call that may read them or clobber them and at every exit. Deoptimization, leaving, and the exception return all pass through one exit that stores them, so the write-backs, initialized flags, completed steps, and the block reached are exactly the interpreter's.

**Memory.** Code is written into a private read-write mapping that is then made read-execute (`mmap`, then `mprotect`) and never written again: no mapping is writable and executable at once. On Linux AArch64 the instruction cache is cleared before the mapping becomes executable. On Apple silicon the mapping is a `MAP_JIT` mapping, which the writing thread switches between writable and executable with `pthread_jit_write_protect_np`, followed by `sys_icache_invalidate`; a macOS executable signed with the hardened runtime needs the `com.apple.security.cs.allow-jit` entitlement for that ([Code signing](CodeSigning)). A region whose code cannot be generated (for example a branch beyond an AArch64 branch's range) or mapped runs on the interpreter, and `--tier-stats` counts it with the reason.

**Why it is not observable.** The generated code performs the region program's ops in program order with the interpreter's semantics, and everything outside the ops (the entry checks, the constant loads, the write-back, the step, profile, and task counts, the statistics) is the executor's code, shared with the interpreter. `NEURA_TIER_CHECK=1` checks native regions against tier 1 exactly as it checks interpreted ones, and `NEURA_TIER_CHECK=2` checks whole runs, native code included, against a shadow run at tier 1 (below).

**Platforms.** `--jit=auto`, the default, enables native code only where its generated code has been run and checked:

| Platform | `auto` | `on` | Verified |
| --- | --- | --- | --- |
| x86-64 Linux | native code | native code | by execution: unit tests, the tier 2 suite, and byte-for-byte runtime identity against tier 0 |
| AArch64 Linux | interpreter | native code (experimental) | encodings against an assembler's, and generation of the unit-test programs; not by execution |
| AArch64 macOS | interpreter | native code (experimental) | as AArch64 Linux; the `MAP_JIT` path is not run |
| x86-64 macOS | interpreter | native code (experimental) | the x86-64 code generator as on Linux; the macOS mapping path is not run |
| Others (Windows, other processors) | interpreter | an error | no code generator |

`--jit=on` starts by running a small generated program; when it cannot be mapped or does not run as generated, or there is no code generator for the processor and system, the run fails before it starts. `auto` uses the interpreter in those cases, silently. A CI job definition (`.github/workflows/jit.yml`) runs the identity comparison with `--jit=on` on AArch64 Linux and macOS runners, so `auto` can be extended once it passes there.

Native code is not the [native capability](Tooling#build-and-run-executables): `--deny-native` governs C code a program calls through `import:c` and `Std.DynamicForeign`, and does not turn the code generator off. Parallel items, which run on worker threads, share the cache's code: published code is immutable, and each run keeps its own context and registers.

#### Controls

- `--tier=0|1|2` on `neura run` and `neura test` (`RunLimits::tier`) sets the highest tier; 2 is the default. Tiers 1 and 2 are not used with a graph device, which evaluates the graphs it accepts.
- `NEURA_TIER=0` or `NEURA_TIER=1` in the environment lowers the tier of every run in the process, the test suite's included. `NEURA_RUN_OPTIONS` may lower the tier of a [native executable](Standalone) with `--tier=0` or `--tier=1`. Nothing raises it.
- `--jit=off|on|auto` on `neura run` and `neura test` (`RunLimits::jit`) chooses between native code and the interpreter for regions (above); `auto` is the default. `NEURA_JIT=off|on|auto` in the environment applies to every run in the process, the test suite's included, and combines with the option: `off` from either wins, then `on` from either. `NEURA_RUN_OPTIONS` accepts `--jit` for a native executable. `NEURA_JIT_DUMP=1` writes each compiled region's code, in hexadecimal, to standard error (or to the file it names).
- `--tier-stats` prints, after the run, the blocks lifted (by hint and by search), the proof and search time, the steps each tier ran (tier 2 counts the steps run inside regions), why blocks stayed on tier 0, the blocks that ran most steps on tier 0, the regions formed, how often regions were entered, left, and deoptimized and why, the blocks where they deoptimized and left most, and for native code the mode, the regions compiled and their bytes of code, the regions left on the interpreter and why, and how many entries ran native code. These lines are diagnostics, not part of the invariants above: they depend on timing and threads. `--stats` is unchanged, so its output is identical at every tier.
- The last line of `--tier-stats` divides the wall time of the command among what the runtime was doing, in milliseconds: `tier: time: total T ms: load L, proving P, searching S, tier 0 Z, tier 1 D, regions R, collection C, host H, other O`. The total runs from a clock reading before the image is read (for `neura test`, before its built image is loaded; for a native executable, when the runner starts the run, after the image has been decoded) to one after the other statistics are printed. *Load* is reading, decoding, and validating the image and setting up each execution, up to its first step. *Proving* and *searching* are the time tier 1 spent proving hints and searching for forms on the run's thread, as measured for the first line, and are not counted again in tier 0 or tier 1. *Tier 0* is steps evaluated by reference, declined lifted steps included. *Tier 1* is lifted, wired, and empty steps with the commits of their exits (calls, returns, state operations), and forming regions and compiling them to native code, which has no category of its own. *Regions* is the time inside tier 2 regions, interpreted or native, with their helpers. *Collection* is garbage collection, wherever it was triggered. *Host* runs from a host request, poll, or wait leaving the execution to the execution's next step: the service, console output, file and network I/O, waiting for completions, and applying them; a callback's steps count as steps. *Other* is the total less every other category (scheduling decisions, the runner's work between and after runs, the statistics), clamped at zero. Every moment belongs to one category, so the figures sum to the total within rounding. The steady clock is read only when the category changes (a region's entry, a step at another tier than the step before, a collection, a host request, a scheduling decision), never per step, and nothing depends on the times; without `--tier-stats` nothing is timed. Each change of category costs one clock reading, so a program that enters regions millions of times runs measurably slower with the option than without it (about a fifth slower for `tests/bench-wall/neura/binary-trees.nra`), and the readings' own time is counted in the categories they separate. `run --each` and `neura test` time their executions, which run one after another, on one timeline, and parallel items evaluated in order belong to their run's. With a graph device, a fleet included, or more than one parallel worker, whose threads' time overlaps the run's, the line is omitted.
- `NEURA_TIER_CHECK=1` evaluates every block that tier 1 runs by reference as well, and runs every region execution again at tier 1: the region runs, everything it changed is put back (slots and their flags, the block, the step, per-function, task, and poll counts, and each write to heap or global storage, from a log), the same blocks run at tier 1, and the two must agree on the block reached, every slot and flag of the frame, the counts, and the writes to storage, in order and with their values. Reads are covered by the slots they feed. It aborts the process with a report on any difference. It is a debugging aid.
- `NEURA_TIER_CHECK=2` runs every execution that would run above tier 1 beside a **shadow**: a second execution of the same image, arguments, limits, and initial state, restricted to tier 1 (no regions, no native code, no check of its own). The run itself runs as in production, regions and native code included; the region check of `NEURA_TIER_CHECK=1` is not used. The shadow shares the image and the tier cache's lowered blocks, which are immutable once published; its counts of block executions join the run's, which changes only when blocks are lifted. It has its own heap, frames, globals, scheduler, and counters, and no host services, observer, task dump, or timeline: it makes no host request, writes nothing, and loads no native library. The two are compared at every return of compiled code to the dispatcher, at every event the run hands to its caller (a host request, poll, wait, cancel, completion, or trap), and after each callback a host service makes. The shadow first runs, step by step, to the run's step count; an event before it, or a step past it, is a difference. Then, in this order: the step count; whether each has finished or trapped, and a trap's kind, reason, detail text, function, block, and callers; the event, and for a host request its import and every argument; the frames, from the bottom, each with its function, block, return slot and block, and every slot's initialized flag and, when it is initialized, its value; every global and its flag; the last handle, live and peak heap cells, and the collection threshold; the steps of each function under `--profile`; in an image with tasks, every field of the scheduler: every task (its state, frames, scopes, select arms, parked operation, and counters), the runnable queue, the scheduler's counters and next identities, every scope record, channel (its buffer and its queues of senders and receivers, in order), timer and guard (with their queues of waiters), armed deadline, pending request, and cancellation, and the totals of released tasks by spawn site; and the host requests issued, identity numbers given, the request the run waits for, the parallel items outstanding, and the constants. The tier machinery (block plans, tier counts and statistics, region registers), scratch buffers that each step overwrites before reading, and caches built from the image are not compared: they differ between the run and its shadow by design and decide only how a block is evaluated. At the end of the run, at every one of these points under `NEURA_TIER_CHECK_HEAP=1`, and otherwise at a point where at least 64 points and at least 2 steps for each live heap entry found at the last such comparison have passed since it, the heaps are compared too, entry by entry in handle order: presence, kind, type, cells and their initialized flags, bytes, list version, and identity number. The bits of an uninitialized slot, field, or global cannot be read, and are not compared. The first difference aborts the process with a report on standard error: `neura: NEURA_TIER_CHECK: the shadow run differs at step N`, where compiled code was last entered, the last sync point, where the run is, the item, and its value in each. What enters the run from outside is given to the shadow after the run has taken it, through the same calls of `nvm::Execution`: completions, deliveries, clock readings, and callbacks, whose own host requests the shadow makes against the run's recorded completions. Parallel items evaluated in order each have a shadow. A run with a graph device, a schedule chooser (`neura test --schedules` and `--schedule`), more than one parallel worker, as a member of a fleet, or under `--replay` is not checked (a run under `--record` is checked); it says so in one line on standard error, `neura: NEURA_TIER_CHECK=2 is not applied:` and why, once per process for each reason, and runs as it would without the variable. Without the variable, nothing of this runs. It is a debugging aid, and a checked run is several times slower.
- `NEURA_TIER_EAGER=1` lifts every block the first time it runs, with ample proof work and search time, and forms every region at its first arrival, so that short runs exercise tiers 1 and 2; it too changes only which blocks run lifted or in regions, and when. `NEURA_TIER_DUMP=1` prints each region program as it is formed.

#### Why the result does not depend on the tier

A lifted block is used only when the structural proof shows that the graph is the circuit library's construction of its typed operations, and the overflow proof shows that reference evaluation of that graph neither overflows nor yields an output lane other than 0 or 1 for any input. The lowering computes each of those operations exactly, with the circuits' failure conditions, so its exit and values equal those the reference evaluator would produce, lane for lane, and the reference evaluator could not have trapped. Everything around the evaluation (charging, input checks, the commit, every state operation and host interaction) is the reference code. Which blocks happen to be lifted, and when, depends on thresholds, time budgets, and thread timing, but it can change only the speed of a run.

A region runs blocks that tier 1 would run lifted, wired, or empty, computes each with the same operations, and commits each exit as the reference commit does: values against the state before the block, assignments in parallel, the state operation with the reference code. What it does differently is not observable: it keeps slots in registers between blocks but writes them back before anything else could read them, since the region allocates nothing, calls nothing, and makes no request; it adds steps in bulk, but the budget check keeps every limit, quantum, and fleet round out of reach until tier 1 runs; and anything that fails, or any exit it does not take, puts the frame back to the block's entry state for tier 1 to run the block exactly as it would have. Which regions exist, and when, depends on counts and on what tier 1 has proven, so it too changes only the speed of a run. Native code is the same region program, compiled op for op with the interpreter's semantics and the interpreter's helpers for the rest, so it changes only the speed too.

## Execution state

Each run owns its call stack, heap, argument values, pending continuation, resource counters, and host bindings. Starting a fresh run creates fresh state from the image and the launch inputs. The root frame receives the UTF-8 argument array. A function frame has typed slots for parameters, locals, and temporaries. Parameters are initialized on entry and remaining slots begin uninitialized. Reading an uninitialized slot traps. The implementation may use a faster internal layout if the observable behavior is identical.

A normal block transition proceeds in this order:

1. Resolve graph inputs from the current frame and constant pool. Check types, initialization, and applicable limits.
2. Evaluate the graph and decode the selector.
3. Resolve the selected exit's values and slot assignments from the pre-transition frame, constants, and graph outputs. Check the exit, payload types, and destinations.
4. Commit the exit's slot assignments in parallel. Perform the exit action. A call, heap request, or host request records its continuation before control transfers.
5. Enter the destination block, return to the caller, or finish execution.

The parallel assignment rule lets a block swap two slots without an ordering dependency. Exit descriptors for unselected paths have no effects. For short-circuit expressions, the right operand's block is reached only when the left operand selects it. Compiling pure alternatives into a single data-selection graph is valid when the source contract permits both computations to be evaluated.

| Exit | NVM action |
| --- | --- |
| Continue | Enter the given block in the current function. |
| Call | Push a frame with the resolved arguments and enter the selected function. The caller retains the resume block and result slot. |
| Return | Pop the frame, place the result in the caller's result slot if present, and enter the caller's resume block. Returning from the entry frame completes the run. |
| State operation | Perform the specified checked heap or global storage operation, or call a built-in kernel ([Kernel calls](#kernel-calls)), store its result if present, and enter the resume block. |
| Host call | Invoke the bound service with the resolved arguments and resume on the declared success or failure continuation. |
| Trap | Terminate the run with the specified runtime fault. |

Direct calls name a function in execution metadata. Dynamic dispatch reads the receiver's type tag and uses a graph-selected exit to choose a compatible function. NVM checks the handle and call signature at the boundary. A graph can implement selection as a decision tree across blocks when a single graph would make the dispatch unnecessarily large.

## Fleets

A fleet advances independent executions of one image. Each member owns its frames, globals, heap, limits, and counters. A round considers a bounded window of unfinished members and may evaluate their graphs together. Only the lowest-numbered member whose final event is still unreported can issue a host request. The caller completes that request or serves a callback before the member continues. Final events arrive in member order. The resulting host requests, responses, and final events follow the same order as running the members one at a time.

The head can always start. Other members can start while the sum of the live heap cells of started, unfinished members is below one member’s heap limit. Admission counts initial constants and arguments as soon as a member starts, including before its first graph step. Once admitted, a member keeps running under its own limits. Aggregate process memory can exceed the limit of one member.

When no device is set and every member has been admitted, the reference executor can group rounds until the head reaches its next event. Other runnable members advance through the same number of rounds, stopping at their first event. Each member sees the same inputs and state, and no admission or host response can intervene during the group. The visible events and round count remain those of the individual rounds.

Fleet admission tracks live heap cells as they change. Finishing a member removes its remaining cells from the total before another member is admitted. With a graph device, the fleet checks graph input reads before placement and can defer packing their lanes until evaluation. The begun frame and constants stay unchanged in between. An automatic device can request full jobs only for the graph indices it selects. Other devices receive the eager batch, and every declined step uses the reference evaluator.

## Heap and objects

Objects have a runtime type tag, a layout ID, and typed field slots. Layouts preserve inherited fields at stable indices. A method receives the object handle as an explicit argument. Each object has independent storage, while calls share the compiled method graphs. Collections use typed element slots, and lengths and indices are checked before accessing storage.

Object and interface references can carry nil as handle zero. The collector skips it, and field access, virtual dispatch, and destruction fault when they try to dereference it. A type test returns false for nil, and a checked cast preserves it. Class identity operations give a live object a sequence number when its default hash or text is first requested. The number stays with the object and depends on request order.

An allocation creates a fresh handle and uninitialized fields. Compiler-generated constructor control flow performs base initialization, field initialization, and the declared constructor body in language order. It exposes the result of `new` on successful completion. If the language permits a field to be initialized later, its slot remains uninitialized until a store. A premature load traps. Field and collection stores validate the handle, layout, index, and value type before changing storage. Compiler-generated destruction calls the required cleanup methods and then invalidates the handle. Freed handles cannot name later allocations. These rules define runtime checks. The language specification defines which source operations are legal and the ordering of language-visible initialization and cleanup.

For example, incrementing a counter runs a block that requests a field read, a graph that adds to the returned value, and a block that requests a field write. The heap handler performs the read and write. The graph supplies the new value.

### Garbage collection

NVM uses a non-moving tracing collector. The root set comprises reference constants, initialized reference globals, and initialized reference slots in every active frame. Temporary references also remain rooted while constructing the launch arguments, allocating a collection from its already evaluated elements, or appending an element after the exit's parallel assignments. NVM traces initialized reference fields by the object's actual layout and visits reference elements in arrays and lists. Text and byte storage are leaves. Numeric slots never keep an object alive even when their bits match its handle.

Allocation and list growth are safepoints. The collector marks reachable entries iteratively and sweeps the remaining entries, including unreachable cycles. It attempts collection before an allocation or growth would exceed the configured heap limit. It also collects at a soft threshold that grows with the retained heap, so workloads that release objects can reclaim space before reaching the hard limit. Collection does not consume program steps and uses no clocks or background threads. An initialized frame slot retains its reference until the slot is overwritten or its frame returns.

The collector caches the reference positions in each encountered object layout and frame signature. Subsequent traces visit those positions directly and skip scalar cells.

Collection reclaims storage without invoking language cleanup methods. An explicit `destroy` runs its compiled cleanup and invalidates the object immediately. Both reclaimed and explicitly destroyed handles remain invalid, and every new allocation receives a fresh handle. The run's handle limit counts all assigned handles independently of reclaimed storage. Programs must keep references in typed storage across safepoints to retain their targets.

## Host calls and standard output

A host import declares a service name, interface version, typed arguments, and typed success and error results. An exit references an import by table index. At load time the runtime binds each declared import to a registered service with the same signature and version under the runner's service policy. Imports grant access only to their bound service. A service that needs filesystem or network access defines that authority in its own interface and configuration.

A request contains the import, resolved arguments, and an execution-local sequence number. NVM issues the request once on entering the selected exit. A completion supplies either the success or error value. The runtime type-checks that value, writes the designated result slot, and enters the corresponding resume block. A suspended run keeps the pending request and resumes from its completion. The execution contract covers a live run. Durable recovery across a process crash requires a separate persistence protocol.

Host services receive copied values. Booleans, integers, and floating-point values keep their slot bit encodings. Strings, byte arrays, and byte lists use byte sequences. Other arrays and lists transfer their elements in index order, and tuples transfer their fields in declaration order. Host signatures describe these shapes recursively without image-local type indices. The runner limits copied elements and bytes using the heap-cell budget and bounds the nesting depth. Handles remain inside NVM, and a compound completion allocates fresh VM storage with its partially constructed values rooted until completion.

A terminal completion from `neura.process.exit` version 1 ends only the current NVM execution with the supplied status from 0 through 255. A recorder stores that completion and replay returns the same terminal result without invoking the service. The runner must register the service before an image can call it.

The standard console service is `neura.console.write_line` version 1. It takes a UTF-8 string and returns either success with no payload or an unsigned 32-bit error code. Error code 1 denotes a failed write. It emits the string's bytes followed by a single LF byte, independent of platform newline conventions. A host write can partially succeed before reporting failure. The runtime reports the failure without retrying. The language library determines how that result appears to source code.

**Native calls.** A `neura.ffi.call` signature is a version byte (1), a little-endian `uint16` fixed-argument count (65535 for a function that is not variadic), a `uint16` argument count, the result type, and each argument type. A type is one tag: 0 void, 1 `_Bool`, 2 through 9 the signed and unsigned 8-, 16-, 32-, and 64-bit integers, 10 `float`, 11 `double`, 12 a pointer, or 13 a struct followed by a `uint16` member count and the member types. Arguments are the values' bytes back to back in native byte order, each exactly its type's size, and the result is the result type's bytes. A variadic argument must not be a `float` or an integer narrower than `int`. A malformed signature or argument list fails with code 4 before the call. The runner frees every arena and unloads every library when a run ends. Native code runs in the runner's process, outside the NVM's checks ([Foreign interop](ForeignInterop)).

A read requests at most 1 MiB, and so does an entropy request. A run holds at most 1,024 open file IDs and 1,024 open socket IDs; an open beyond that fails with code 100. When a run ends, by completion, trap, or process exit, the runner closes every file and socket it left open. `neura test` does the same after each test.

**Capabilities.** The console services and `neura.process.exit` are always available. Every other service belongs to a group (files, network, environment, clock, entropy, and native) that a runner grants or denies. The `neura` command-line tools start with every group granted, and `--deny-fs`, `--deny-net`, `--deny-env`, `--deny-clock`, `--deny-entropy`, `--deny-native`, and `--deny-all` turn groups off; `--allow-*` options, including `--allow-fs=prefix,...`, grant them again in command-line order. The C++ type `nvm::Capabilities` that an embedder passes to the providers denies every group until the embedder grants it. A service that is not granted still binds, and each call fails with code 14. With path prefixes, the provider resolves each path to an absolute path the way the operating system would, following symbolic links, and allows it only at or below a resolved prefix; operations on an entry itself (remove, rename, make directory, stat without following links, create) check the resolved parent and the final name. The check and the operating-system call are not atomic.

A failed console write traps with reason 3 when it comes from `Console.print_line`; the other console forms return the failure as an `Io` error. For `console.print_line("Hello, World!")`, the image stores the string in its constant pool. A graph selects a host-call exit whose argument names that constant. The bound console handler writes the line and NVM resumes at the exit's success block. The entry function's `ExitCode` becomes the process status. A trap yields a diagnostic, and `nvm::exit_status` gives the process status for its class, the `Std.Program.ExitCode` variant that names it ([Errors](Errors)). The embedding API exposes the full status or structured trap independently of the platform's exit-code range.

The test assertion services `neura.test.assert` and `neura.test.assert_equal_int32` are retired along with the built-in `Test` module. An image built earlier that imports them fails to bind, before it runs; an earlier image whose only import is `neura.console.write_line` still runs.

**Overlapping and cancellable services.** In an image with tasks, a service may declare that it *overlaps* (`HostService::overlapping`): the task that calls it parks, the other tasks run, and the completion is delivered at a later scheduling point ([Concurrency, section 10.4](Concurrency#104-host-io)). The standard overlapping services are `neura.net.connect`, `accept`, `read`, and `write`, `neura.console.read`, and `neura.clock.sleep`. Each exists twice: version 1 keeps its contract and overlaps without being cancellable, and version 2, which has the same signature and behavior, is the cancellable form the library binds. A cancel request reaches a version 2 request when its task's scope is cancelled while the request is pending. The provider then answers exactly once: with the completion, if the operation finished before the cancel request was processed, and otherwise with error 15 (`Cancelled`; the library's `IoErrorKind.Cancelled`). A write that stored some bytes completes with that count, so a cancelled write with nothing stored answers 15 and one that stored a prefix reports the prefix. `neura.net.connect` resolves the name before it returns, so name resolution holds up every task for its duration. File services, console writes, and every other service complete before the scheduler continues. Without tasks, every service is served as before, version 2 included.

A service starts an overlapping request with `begin`, which returns the completion when the operation finished at once and otherwise a `PendingOperation`: the descriptor to wait for, an optional deadline on the run's task clock, and an `attempt` function that tries to finish without blocking. The driver (`src/nvm/driver.hpp`) is the only code that waits. It keeps the pending operations by sequence number and, at every scheduling point, checks them without blocking (`poll(2)` with a zero timeout over their descriptors, and the clock against their deadlines), then delivers the answers in ascending sequence order and reads the clock when a timer is armed. When no task can run it blocks in `poll(2)` until a descriptor is ready or the earliest deadline passes. It starts no thread. A clock that reports virtual time is never waited on: the driver moves it to the earliest deadline instead.

## Kernel calls

A kernel exit (NVR 1.6, state operation 24) calls one of the built-in C kernels compiled into the runtime ([Kernels](Kernels)) through the image's `KERN` record. The loader has already checked that the runtime has the kernel at the record's ABI version and that the signature is the kernel's. The NVM performs the call in this order:

1. **Resolve the arguments.** Each reference argument is checked like an operand of any state operation. Text, an NVR byte string, and an `int64` or `uint64` array or list are viewed in place. Any other array or list is packed into a buffer that the execution reuses: a byte per `uint8` element, and so on. A writable view and a state are packed too.
2. **Charge the steps.** The kernel's step charge is evaluated on the arguments' lengths and scalar values and added to `steps` before the kernel runs. If it would take `steps` past `--max-steps`, the run stops with the step-limit trap at this exit, as a block step would. With `--profile`, the steps count for the function that made the call and for the running task. The charge depends only on the arguments, so the count, and the point at which a step limit stops a run, are the same in every execution mode and on every host.
3. **Run the kernel.** Each output buffer is sized from its declared capacity formula; scratch space from its declared size. A kernel that still reports `NEURA_NEED_CAPACITY` is called again once with the reported capacity and no second charge. A `NEURA_TRAP_*` status stops the run with the program trap (reason 3) and the status's message, the same trap and text as the Neura code the kernel replaces. A `NEURA_ERR_*` status of a kernel with an outcome result becomes the outcome's status and error offset.
4. **Write back and allocate.** Writable views and states are copied back into their arrays or lists only when the kernel did not trap. A text, bytes, or outcome result is then allocated through the allocator that `ConstructText` and collection allocation use: the same handle order, heap-cell accounting, safepoint, and collection schedule. The outcome tuple's value is allocated first and kept rooted while the tuple is allocated.

A kernel call is not a host request. It issues no request and needs no import or capability, so nothing is written to a `--record` trace, `--replay` needs nothing for it, and `--deny-native` and the other capability flags do not affect it. It runs the same way in a task, in an isolated parallel item, in a fleet member, and in the static launcher. `--stats` does not count kernel calls: its fixed figures are part of the cross-mode agreement above, and the steps already include each call's charge.

**What a kernel must guarantee.** A kernel reads only its arguments and writes only the buffers, state, and result locations it is given; it keeps no state between calls except the state byte array the caller holds; it never allocates, calls back, or reads the clock, the environment, the locale, or a file; and it gives the same results and statuses for the same arguments on every platform, with IEEE 754 binary64 arithmetic without contraction and canonical NaNs. Its step charge and buffer formulas are functions of the argument lengths and scalar values only, its charge covers the most work those arguments allow within a constant factor, so no call does unbounded work for a bounded charge ([Step charges](Kernels#running-a-kernel)), and its capacity formulas are always large enough. These are the rules of `src/kernels/neura_kernel.h`; a kernel that breaks one breaks the determinism of every image that calls it.

## Callbacks

An image's `CALB` table names functions that a host service may call while it serves a request ([NVR](NVR#imports-and-optional-source-maps)). The runner passes each request a callback context. Calling a callback runs that function on the same heap and globals, above the frame suspended at the host call, until it returns; the host requests it makes are served the same way, so callbacks can nest. Steps, frames, and heap cells count against the run's limits.

A trap, a process exit, or a failed limit during a callback ends the run. The callback returns nothing to the service, the service's eventual response is ignored, and the run reports how it ended. `nvm::Execution::invoke_callback` is the embedding interface.

`Std.DynamicForeign` registers `neura.ffi.upcall` version 1 with parameters `int64 stub, uint8 list arguments` and result `uint8 list`. `neura.ffi.upcall.create(int64 arena, int64 stub, uint8 list signature) → int64 address` returns a native function pointer, a libffi closure, that packs its arguments as `neura.ffi.call` does and calls the callback with them. It writes the packed result back to native code. A stub is valid only while its arena is open and while a `neura.ffi.call` from the same run is in progress; native code that calls it at any other time ends the process with status 134 and a message on standard error. A variadic signature cannot be an upcall.

## Determinism, limits, and observability

Given the same validated image, initial inputs, resource limits, and host completion trace, a run yields the same exit selections, effects, state updates, and terminal outcome. Clock readings, file contents, and similar external responses enter through the host boundary. Tests can supply those responses from a trace and verify the emitted request sequence. `nvm::record` runs an image with bound services and records each request, as the import's name and version with its arguments, together with the response and the terminal outcome. `neura run --record <file>` writes such a trace as text, and `neura run --replay <file>` answers every request from one without invoking any service or needing any capability. The text form starts with `neura-trace 1`, `neura-trace 2` when it records callbacks, or `neura-trace 3` for an image with tasks (see "Traces of images with tasks" below); each `request <import> <version> <arguments>` line is followed by `ok <value>`, `error <value>`, or `exit <status>`, and the file ends with `outcome completed <status>` or `outcome trap <kind> <reason> "<message>"`. Values are unsigned decimal slot bits, quoted byte strings with `\xHH`, `\n`, `\r`, `\t`, `\"`, and `\\` escapes, or bracketed lists; `#` lines are comments. Between a request line and its response, `callback <name> <version> <arguments>` opens a callback the service made, followed by the requests the callback made and `return <value>`, or `ended` when the run ended during it. A replay calls each recorded callback with its recorded arguments before supplying the request's response, and checks that the callback makes the recorded requests and returns the recorded value. A replay reproduces the console output the recorded requests wrote, and a divergence ends with status 1 and a description of the first differing request. `nvm::replay` runs an image, answering each request from a recorded trace instead of real services, and reports whether the image made the same requests in the same order and ended the same way. Requests match by import name and version, not table index, so two images that number their imports differently can be compared. The decompiler tests use this to compare an image with one regenerated from its decompilation. The reference executor runs one block at a time and waits for each selected host call before resuming, except for a service that overlaps in an image with tasks ([Host services](#host-services)). A faster executor must preserve that order where it is observable. Fleets may advance independent runs together while preserving their serial order where it is observable.

NVR 1.5 adds scheduler exits, a poll bit on continue and call exits, and a `TRNS` table of transferable layouts ([NVR](NVR#scheduler-operations-15)). The compiler emits them for a program that uses tasks, after checking at source level that what tasks exchange is transferable and what they call is task-safe, and the NVM runs such an image on one deterministic scheduler ([The scheduler](#the-scheduler)). `RunLimits` supplies `max_tasks` (65,536 by default), `max_queued_messages` (1,048,576), `max_pending_requests` (4,096), `task_quantum` (1,024 polls), and `parallel_workers` (1). [Concurrency](Concurrency) specifies the language and [Status](Status) what this release supports.

The loader applies size and count limits before allocating image structures. The runner enforces declared bounds on frame depth, live heap storage, execution steps, and, for an image with tasks, live tasks, values buffered in channels, and overlapping host requests in flight. The task quantum is a scheduling setting rather than a work limit. In a task image, each live frame of every task counts toward the heap-cell limit as one cell plus one per slot, and so do the scheduler's records: 20 cells for a task, 1 for an open scope, 16 for a channel and one more for each buffered message, 8 for a timer, 8 for a guard, and 8 plus the cells of its argument for a parallel-map item. Images without a `TRNS` table keep the previous accounting. Exhaustion traps at the operation that exceeds the configured limit. Limit checks occur before the affected allocation or state mutation. A trap stops further program execution and leaves any completed external effects visible.

Diagnostics identify the runtime fault and, when execution has begun, the function and block. Optional source maps add source locations. A trace can expose block entries, graph exits, and requests and responses. Inspection and decompilation use the executable graph and continuation tables, with source maps as supplemental information.

### The scheduler

An image with a `TRNS` table has tasks. One scheduler runs one task at a time. Its state (task records, the runnable queue, channel buffers and waiter queues, cancellation signals, timers, guards, and pending host requests) is NVM state reached through scheduler exits, as the heap is reached through state operations. [Concurrency, section 10](Concurrency#10-runtime) is the contract for programs; this section states what the runtime does.

- **Queues and identity.** The runnable queue and every waiter queue are FIFO. The root task is task 0, and tasks, channels, and timers are numbered in creation order.
- **Decisions and ticks.** A scheduling decision takes a task from the runnable queue and runs it until its turn ends. The tick is the number of decisions made so far (`Execution::tick()`).
- **When a turn ends.** A turn ends when the task parks, when it finishes, or at a poll that finds the quantum spent. A poll is a bit on a continue or call exit, and each one the running task executes adds one to its count for the turn. When the count reaches the quantum, the task goes to the back of the runnable queue if another task is runnable, or if a deadline, a timer, or a host request is outstanding. With nothing else runnable and nothing outstanding, the count restarts and the task keeps running. The second condition gives the driver a scheduling point at which to read the clock and deliver completions while one task computes, so a scope's deadline stops a task that never parks. An image that arms no timer or deadline and issues no overlapping request is scheduled as if that condition did not exist.
- **What the driver sees.** `Execution::advance()` returns to its caller at every host request. Before a decision, while a timer, a deadline, or an overlapping request is outstanding, it returns a `Poll` event; when no task can run but a timer or a request can still wake one, a `Waiting` event; and when a task waiting for a cancellable request was cancelled, a `Cancel` event. The driver answers with `deliver()` for a completed request and with `advance_clock(now)` for a clock reading, which expires the timers and deadlines at or before it. When no task can run, nothing is outstanding, and at least one task is parked, the run ends with the `deadlock` trap.
- **The clock.** Timers and deadlines are readings of a `TaskClock` that the driver supplies: `now()` and `wait_until(deadline)`. The default is the host's steady clock, which is the clock of `neura.clock.monotonic`. `VirtualTaskClock` is the clock of `--virtual-time`: it starts at zero, `wait_until` moves it to the deadline without waiting, and the driver never blocks on it. `StandardServices::set_clock` gives the same clock to the clock services: `neura.clock.monotonic` returns its reading, `neura.clock.wall` its reading after 2000-01-01T00:00:00Z, and a `neura.clock.sleep` that does not overlap moves it by the sleep's length. The clock capability is checked first in each case. When every task is parked, descriptors are pending, and a deadline is armed, the driver moves a virtual clock to the deadline and then checks the descriptors once, so under virtual time a deadline is not held back by I/O that is not ready.
- **Choosing a task.** The reference scheduler takes the first runnable task. `RunLimits::chooser` replaces that choice: a `ScheduleChooser` is called at each decision with the tick and the number of runnable tasks and returns the position in the runnable queue of the task to run. Zero is the reference scheduler's choice, and a position beyond the queue is taken as zero. Every choice is a legal schedule, because only the order among runnable tasks varies. `ExploringChooser` picks uniformly from a seed with a fixed generator (SplitMix64), so a seed names the same schedule on every machine, and keeps each choice that was not the first; `RecordedChooser` replays such a list and reports a position that did not exist. `neura test --schedules` and `--schedule` use them, and `write_schedule` and `read_schedule` in `src/nvm/schedule.hpp` write and read the saved file ([Concurrency, section 14.4](Concurrency#144-testing-concurrent-code)). A chooser decides only among runnable tasks; it does not decide when a host completion is delivered. `RunLimits::schedule` receives the task chosen at each tick, for tests and tools that compare schedules.
- **Observation.** `Execution::dump_tasks()` returns a snapshot of every task, `RunLimits::observer` receives scheduler events, and `RunLimits::profile` adds totals for each spawn site. None of them changes the run.

### Traces of images with tasks

An image with a `TRNS` table records and replays with trace file version 3, which only such an image writes; a trace of any other image stays version 1 or 2, byte for byte as before. The file adds a `settings` line, the issuing task and tick to every request, and the driver's own actions:

```text
neura-trace 3
settings quantum <n> max-tasks <n> max-queued-messages <n> max-pending-requests <n>
request <import> <version> <arguments> task <id> tick <n> [overlapping | cancellable]
ok <value> | error <value> | exit <status> | abandoned
...
deliver <tick> <request> [cancelled]
clock <tick> <nanoseconds>
outcome completed <status> | outcome trap <kind> <reason> "<message>"
```

- `settings` holds the quantum and the scheduler limits of the recorded run. **A replay uses them in place of its own**: `neura run --replay` with another `--task-quantum` or `--max-tasks` still reproduces the run.
- `task` is the task that issued the request and `tick` the number of scheduling decisions made when it did. A request without a mode completed before the scheduler continued. `overlapping` and `cancellable` mark a request that parked its task, by the mode of the service that served it. Its completion line follows the request line, as for every request, though it was delivered later. `abandoned` replaces the completion of an overlapping request the run ended without delivering.
- The `deliver` and `clock` lines follow the last request, in the order they happened. `deliver` names a request by its position among the request lines, from zero, and the tick of the scheduling point where the driver gave the task its completion. `cancelled` says that a cancel request had reached the operation before its answer was delivered, whichever answer it was; the answer is the completion if the operation had finished, and error 15 otherwise. `clock` is a reading of the run's monotonic clock, in nanoseconds, that expired at least one timer or scope deadline; other readings are not recorded. Readings can be negative only in a hand-written trace.
- The outcome gains the trap kinds of the scheduler, among them `deadlock`, `task-limit`, `request-limit`, and `message-limit`. A deadlock is its own outcome and has no message.

A replay invokes no service and needs no capability. At a request it checks the import, the version, the arguments, the issuing task, the tick, and whether the request overlaps; a synchronous request is answered from the trace and an overlapping one parks its task. At a scheduling point (a `Poll` or `Waiting` event of the scheduler) at tick *T* it applies, in recorded order, the deliveries and clock readings recorded at *T*, up to and including the first clock reading, because a reading can cancel a scope and the cancel request is processed before the next scheduling point of that tick. The replay stops with status 1 and names the first difference when:

- a request differs from the recorded one (import, arguments, task, tick, or mode);
- a delivery names a request that is not pending, or a recorded event is left behind at a tick the run has passed;
- the run waits at a tick at which the trace records no delivery and no clock reading, or a recorded clock reading expires nothing;
- the run cancelled a request that the trace does not mark `cancelled`, or the trace marks a request `cancelled` that the run never cancelled;
- the run makes fewer requests than recorded, or the outcome differs.

A replay that finishes without a difference has reproduced every scheduling decision, since each of them follows from the image, the settings, and the deliveries. It cannot tell a delivery moved to an earlier scheduling point where the run behaves the same apart from the tick; the recorded request ticks bound that. A trace without the `settings` line (version 1 or 2) replays an image with tasks whose requests all completed before the scheduler continued, under the caller's own quantum and limits. A run under `--virtual-time` writes the same file with its virtual clock readings and replays like any other, without the option. A trace holds no schedule choices: a recorded run is a run of the reference scheduler, and a schedule explored by `neura test` is saved in a file of its own.
